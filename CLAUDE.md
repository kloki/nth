# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

nth ("N-th time") is a personal, opinionated coding harness in Rust: a cargo workspace that builds one `nth` binary. `docs/design.md` is the design doc, `docs/ui.md` the TUI layout spec, and `docs/todo.md` lists what opencode has that nth does not yet (a reference, not a backlog).

## Commands

CI runs these three, and all must pass:

```sh
cargo test --workspace
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
```

- Single test: `cargo test -p nth-tui prompt_and_status_rows_never_move` (any substring of the test path works).
- Run the TUI: `cargo run -p nth`. It needs at least one usable provider: ChatGPT is built in and runs once `nth connect` signs in to your subscription; otherwise run `nth init` and uncomment one, with its API key set (OpenCode Go and Zen read `OPENCODE_API_KEY`). `NTH_MODEL` (or `--model`) picks the model as `provider/model`; with none set, a random one the providers list is used.
- Headless: `cargo run -p nth -- run "<prompt>"` (act mode; `--mode plan` to plan, `--agent <name>` to run as a primary agent; ctrl+c cancels the turn and saves the session, so `nth -c` continues it, and a second ctrl+c exits 130). List models: `cargo run -p nth -- models`. List skills: `cargo run -p nth -- skills`. List agents, subagents and primary ones: `cargo run -p nth -- agents`. List formatters: `cargo run -p nth -- formatters`. List language servers: `cargo run -p nth -- lsp`; what they say about a file: `cargo run -p nth -- lsp diagnostics <file>`. Send a sample desktop notification: `cargo run -p nth -- notify` (`--event needs-you` and others). What the model remembers about the project (`.nth/memory/`): `cargo run -p nth -- memory` (`--json`). What a saved session spent: `cargo run -p nth -- usage [<id>]` (`--all` per day and model, `--json`). Its work plan: `cargo run -p nth -- work [<id>]` (`--json`). The saved sessions of this directory (those that moved from it into a worktree too), newest first: `cargo run -p nth -- session list` (`-n <count>`, `--all` for every directory, `--json`); delete one with its plan, work items, monitor logs and images: `cargo run -p nth -- session delete <id>` (any start of the id; `/copy-id` in the TUI copies it). Sign in to ChatGPT in the browser: `cargo run -p nth -- connect` (`--status`, with `--json`; `--logout`).
- Preview a saved session's next logical request: `cargo run -p nth -- context [<id>]` (`--json`; JSON is automatic when stdout is redirected). It reconstructs from saved state, so another process's unsaved state and inbox are unavailable. Manage repository Curios with `cargo run -p nth -- curio --help` (no provider needed).
- Config: optional `~/.config/nth/config.toml` (or `--config`, `NTH_CONFIG`); `cargo run -p nth -- init` writes one with every key and its default (`--force` to overwrite; the template, `crates/nth-config/src/config.toml`, is the reference for every key, and has OpenCode Go and Zen commented out), and `cargo run -p nth -- config` prints the resolved one. Flags and env vars win over it. Another provider is a `[provider.<id>]` block with `base_url` and `api_key_env`; the id `chatgpt` is reserved for the built-in one.
- A new config key goes into the `nth init` template (`crates/nth-config/src/config.toml`, with its default and a comment) and into the internal `config` skill (`crates/nth-context/src/skills/internal/config/SKILL.md`) in the same change, so both keep listing every key; `every_key_is_in_the_template_and_the_skill` in nth-config fails on one missing from either.

## Architecture

Crates in `crates/`, from the bottom up:

- **nth-directories**: checkout and main-checkout discovery and the shared `.nth` generated-state layout. A session persists its state root so plans and work remain in the main checkout across worktree moves and removal; non-Git sessions use their starting directory. Checkout-specific project discovery remains separate, and existing Curios roots stay authoritative.

- **nth-context**: what nth reads about a project before the first prompt: instruction files (`AGENTS.md`, or `CLAUDE.md` where a project has none), skills (`SKILL.md` folders in the Claude Code, opencode, open-standard and nth places, plus the internal ones nth ships in `skills/internal/` (`init`, opencode's `AGENTS.md` setup; `setup-worktrees`, which writes `.nth/worktree-setup`; `work-plan`; `config`, how to set up `config.toml`; `browser`, which drives a browser with the agent-browser CLI through bash; `screenshot`, which captures the screen, a window or a region with the platform's CLI and reads the file; `curios`, how to author, publish and revise a curio from review comments; `curios-design`, the page contract a curio must keep to and how to design it and draw its diagrams, adapted from Claude's artifact design skills), which a skill file of the same name replaces) and agents (`agents/`: opencode's built-in `general` and `explore`, nth's `clerk` for small one-off tasks such as a commit message, nth's `experimenter`, which settles a question by running something in a git worktree of its own, nth's primary `research` agent, which splits a long investigation across subagents and keeps its findings in `.nth/research/<session>.md`, shown with `show_user`, plus one markdown file per agent in the Claude Code, opencode and nth places, the body being its system prompt; opencode's `mode` frontmatter makes one a `Subagent` (the default), a `Primary` agent you run a session as in place of plan or act (never named `plan` or `act`), or `All`, and `Agents::subagents` and `Agents::primaries` are what the task tool and `/agents` offer), and the project's memory (`memory.rs`: `.nth/memory/` in the main checkout, so worktrees share it, one markdown file per fact with `name`, `description` and `type` (user, feedback, project or reference) frontmatter, and `MEMORY.md`, the index, cut to 200 lines or 25 KB for the system prompt; read only when `Paths::memory`, the config's `[memory] enabled`, is on), found by `Context::discover`, the instruction walk going from the working directory up to the home directory when under it, else to the project root, and the nested ones the read tool attaches (`instructions::nested`, from the folder of a file read or a directory listed); each file brings the ones it names with `@path` outside code (`instructions/imports.rs`, Claude Code's rule: relative to the file, `~` for home, 4 files deep, each file once, a word naming no file left alone since `@explore` is an agent). `instructions::Watch` is what a session's model last saw of those files and of where one more could appear (`Context::absent_instructions`): asked with a stat per file, it returns the files created, edited or removed since. `frontmatter` reads the YAML block skills and agents share. `Paths` carries the home, config and data directories so tests never touch the real ones; `Paths::nth_data` is where nth saves (sessions, `models.json`, the models.dev catalogue kept between runs, and `auth.json`, whose `Store::new` takes it from the CLI). Depends on nothing else in the workspace.
- **nth-protocol**: types every crate shares: `Message`, `Event`, `Mode` (plan or act), and the `Provider` and `Tool` traits. Anything swappable sits behind one of these traits. `Provider::qualify` names a hand-written model id (an agent's frontmatter) as the listing does, `provider/model`; the default leaves it as it is and `Providers` routes it. It re-exports `nth_context::agents::tool_names` (`WRITERS`, `writes_files`, `touches_work`, `WORK_TODO`, `UNTIMED`), the names that agent permissions, plan-mode subagents, the session loop and the TUI decide on. `tool.rs` owns what a failed call leaves: `failed` writes the `Error: ` result, `failure_reason` reads the reason back (the usage ledger and the TUI do), `INTERRUPTED` is the reason when you cut a call short and `timed_out` when the loop's ceiling does. `parse_args` turns any tool's arguments into its struct. `ToolContext::for_call` is the context one call runs in, which `run_call` builds. Also the handles a tool reaches the front-end through, on `ToolContext`: `Asker` (questions), `Screen` (which tab shows), `Monitors` (`monitor/`: the wire types and the registry of running commands, which only passes what they say to the front-end) and `Attachments` (`image.rs`: the `Image`s a tool shows the model beside its text, one per call, which `run_call` puts on the `Message::ToolResult`; an image's bytes live in a file of their own, `path`, and ride along base64 in `data`, which is never saved). `context_preview.rs` (its types re-exported at the crate root) holds the typed next-request `Preview` (its `Entry`s, `ToolDefinition`s, `Budget` and the `Phase` of the turn it was taken at, whose `label()` the TUI shows) and `ContextPreview` (also on nth-session's `FrontEnd`), a `watch` slot holding the newest `Arc<Preview>` the loop published; `builds()` is whether a front-end subscribed or the `context` tool asked (`want`, which the loop's `turn_ended` clears, since a front-end's slot outlives the turn); `reset` empties the slot and the want as a turn or `/compact` starts (and the TUI's as its turn ends, even a panicked one), so whatever it holds during a turn is that turn's; a headless turn builds none until something asks, and a front-end holds a receiver only while its context tab is open during a turn, since one kept between turns would have every later turn build. `Workdir` on `ToolContext` is where a tool moves the session's working directory (the worktree tools), shared by the calls of a turn.
- **nth-llm**: `Provider` impls. One module per wire protocol, each a `Client` that streams one request: `chat_completions` (OpenCode Go or any OpenAI-compatible endpoint, and what a model goes over when the catalogue says nothing else), `messages` (Anthropic messages, for Claude on Zen and MiniMax on Go) and `responses` (OpenAI responses, for GPT on Zen and GPT and Grok on Go). `providers/` is the one `Provider` the front-ends see: an `Endpoint` per `[provider.<id>]` in the config (`endpoint.rs`), each with its three clients, a `Kind` (`Configured`, its key and models, or `ChatGpt`, the login and the efforts its last list offered) and `Endpoint::stream`, which readies a request for the model's wire and sends it, and `listing.rs` for its `/models` and the merged listing. An endpoint signs requests with its `Credentials` (`auth.rs`): an API key, or `ChatGpt` from nth-auth, resolved once per request (refreshing the token) and put on the wire by each client (for ChatGPT the bearer token alone; a plan refusal no wait fixes, such as `subscription_sharing_usage_limit_exceeded`, is never retried, `responses::REFUSAL`); a login that fails is a request error (`stream::Error::Auth`), retried only when the token server could not be reached or answered a 429 or a 5xx, never when you must sign in again or it refused otherwise. `chatgpt.rs` is the one built-in endpoint, `chatgpt`, on OpenAI's public Responses API with a Sign in with ChatGPT token: always responses, OpenAI's catalogue entry for what a model needs on the wire, and its models from OpenAI's list (`GET /v1/models`, which differs by plan and account: the listed, API-supported ones, with its context window and efforts and the catalogue's output limit) at no price; the endpoint remembers the efforts its last list offered, and `stream` snaps a request's effort to those before the catalogue's. It is always among the endpoints but asked `connected()` each time: until then its models are refused (`providers::Error::Auth`) and it is left out of the listing, so connecting mid-run needs nothing rebuilt. A model id is `provider/model`: the prefix routes the request to its endpoint and the rest goes on the wire, and a bare id goes to the default provider (the config model's). `catalog` is models.dev, fetched in the background when `Providers` is built and kept once loaded (`Snapshot`; never by `Providers::offline`, which `nth context` and tests run on); a failed fetch leaves none: callers during the backoff (5 s doubling to 5 minutes, `RETRY_INITIAL` and `RETRY_MAX`) get none at once, callers during a fetch wait on it rather than start their own, and the background task (`Snapshot::refresh`) fetches again as each backoff runs out until one loads, a caller that finds one due first fetching itself, waiting up to the fetch's 5 s timeout. Every fetched catalogue is kept at `models.json` in the data directory (written aside and renamed over; `Providers::new`'s `cache`, which `Runtime::providers` passes), and read back on a blocking thread before the network is asked, by the background task first and by a request that finds nothing served, and served at once, stale but routing each model over its protocol, while the background task keeps trying the network until a fetch replaces it; no request waits on the network while it serves. Its entry for an endpoint is the one with its `base_url` as `api`, else the one keyed by its config id (`provider_for`, so `[provider.openai]` finds OpenAI's); an endpoint with no entry borrows a model's name, limits and efforts from another provider's (`borrowed`: by id, else the part after the last `/`, preferring the `canonical_model_id`), never its price or wire. The listing reads names, limits and the efforts a model takes (`reasoning_options`) from it, and `stream` snaps the request's effort to the nearest of those and dispatches on the `Wire` its SDK for the model maps to, handing the protocol the catalogue's entry for what it needs (an output limit, whether the model reasons, adaptive thinking or a budget on messages). Whether a model takes images is the catalogue's `modalities.input` (`ModelInfo::takes_images`, `None` for a model it does not know, which is sent images; ChatGPT's from OpenAI's `input_modalities`), and `providers/images.rs` rewrites a request's images before it goes out: one whose file was gone at load, one over `MAX_IMAGE_BYTES` (Anthropic's 5 MB of base64), or any for a model that takes none, becomes a note in its result's text, and past 25 MiB or 50 images the oldest become the removal note down to 15 MiB, never those of the latest run of results unless they alone are too many. messages and responses carry a tool result's images inside it; chat completions sends them in one user message after a run of results, since some servers take only text in a `tool` message. A model it does not know, or no catalogue at all, goes over chat completions; one whose protocol nth does not speak (Gemini's) is not listed. A chat completions request carries the session id as `prompt_cache_key` only for a provider on its allowlist of models.dev ids (`chat_completions::takes_cache_key`, asked through `Endpoint::takes_cache_key`), since strict servers refuse unknown fields. `http` is what the protocols share on the wire: the one `reqwest` client, the user agent, the session headers (`x-opencode-session`, `x-opencode-session-id` and, for a subagent, `x-opencode-parent-session-id`), the deadlines and the HTTP facts that decide a retry; `sse` is the line splitting and the `Parser` their streams share, each protocol's `event.rs` giving it, as a plain fn, the events one line holds. `stream` is the rest they share: `Client` (the endpoint's base URL and the route each protocol's own `Client` builds it with) and `send`, the status check (a `Refusal` saying how the protocol reads a refused body), the one `events` loop each protocol's `State` drives as a `Protocol`, `cut`, how each ends a reply cut at the output limit (its text kept as an answer with a note, its tool calls dropped since their arguments are partial), and `Error`, one plain error for every protocol: each classifies what it reports in-stream as it reads it (its `provider_error`, into `Error::Provider` with `retryable` and `overflow`), so `retry_boxed`, which `Providers::retry` calls, reads one type.
- **nth-curios**: repository-local static-document review, independent of sessions and UI. `Store` (`store.rs`) manages `.nth/curios/<session-id>/` at the repository root (`owner_root`, the main checkout through nth-directories, so every worktree finds the same store; `Store::open` builds a session's store from its state root): editable `source/`, private state, immutable published revisions, threads and submitted batches. `Store::new` asks one `git check-ignore` about every path it must find ignored, and walks the whole tree only when `VERIFIED`, the per-process cache keyed by the canonical root, holds no `Stamp` for the root or the base `.nth/curios/.gitignore` changed since; this session's own folder is checked on every construction, but a nested `.gitignore` added later in another session's folder goes unseen until the base `.gitignore` changes or nth restarts. A store call spawns git or waits on a lock another process holds, so async code runs one through `offload` on a blocking thread. `validation.rs` checks published HTML and `host.rs` serves the browser viewer. Use the Curios domain operations rather than editing private state or revisions. `nth-tools/src/curios/` supplies `curio_read`, `curio_publish` and `curio_reply`, which open the calling session's store from `ToolContext`'s `state_root` and `session` on a blocking thread (refused to subagents and agents that do not allow them), and the session delivers submitted feedback through the inbox. Depends on nth-directories only. The CLI is `crates/nth/src/curios.rs`; the TUI's `/curios` and browser hosting are wired in `app/curios.rs`.
- **nth-format**: the formatters run after a tool writes a file: opencode's built-in table (`registry.rs`), each with a probe for whether it applies to the project, plus custom ones from `[format]` in the config. `Formatters::format` runs every match; `nth formatters` prints `Formatters::status`.
- **nth-lsp**: language server diagnostics, LSP written by hand (`transport`, which refuses a message past `MAX_MESSAGE_BYTES` before allocating it, `types`, `client/`). `server/` is opencode's server table (rust-analyzer, typescript-language-server, gopls, pyright and more, used only when on PATH) plus `[lsp]` from the config, with the project-root rules. `Lsp` is one process-wide, cheap-to-clone pool: `touch(path, wait)` starts a client per (server, root) on first use (stopped again once untouched for `[lsp] idle_secs`) and returns the diagnostics (a server that dies, or takes no touch within `TOUCH_TIMEOUT` having stopped reading what it is sent, is dropped from the pool and killed through its entry's cancel token, its status broken with the reason — the unreadable message, else its stderr read to the end — until the next touch starts it again, at most `MAX_RESTARTS` (3) times per root, never reset, after which it stays broken until nth restarts; one that fails to start is not tried again; a start holds the pool weakly, so dropping the last `Lsp` cancels it and kills its server), `status()` is a `watch` of every client's state, `usage()` a `watch` of each server's process and callers, and `report` writes opencode's text for the model. `pool/mod.rs` is the clients' lifecycle, `pool/idle.rs` the touch accounting and idle reaper, and `pool/usage.rs` the usage types, `snapshot` (taken under the clients lock, published after it is released, since a watcher's borrow holds up the publish) and the sampler, a one-second tokio interval the pool owns and aborts when it goes, running while anyone subscribes and reading `/proc` on a blocking thread only for the read. `nth lsp` prints `Lsp::servers_for`.
- **nth-notify**: desktop notifications. `Event::notification` fills the texts in `templates/` from a `Context` (session title, elapsed, last reply); a `Backend` shows them (`notify_send.rs` on Linux, `osascript.rs` on macOS, the platform's by default; `[notify]` picks one via `BackendKind`), and `Notifier` is the cheap-to-clone handle a front-end sends through without waiting. Depends on nothing else in the workspace.
- **nth-icons**: every icon nth draws, as one set (`PLAIN`: Unicode any font has, each icon one column wide) that the TUI and CLI read through `icons()`. A new icon is a field on `Icons`, never a literal at the call site. Depends on nothing else in the workspace.
- **nth-worktree**: git worktrees under `.nth/worktrees` in the main checkout, one per name and on the branch of that name: `open` makes one on first use (the folder ignored by its own `.gitignore`), `changes` says what it has beyond a commit, `remove` deletes it with its branch. Depends on nothing else in the workspace.
- **nth-auth**: signing in to providers that take an account rather than an API key. `Store` is `auth.json` in the data directory (opencode's shape, one entry per provider id, written aside and renamed over with mode 0600). `ChatGpt` is a ChatGPT subscription signed in with OpenAI's Sign in with ChatGPT: `login` runs OAuth with PKCE in the browser (a callback server on `127.0.0.1:1455`, or a free port if taken, written by hand, the pages in `templates/`; it registers nth's own client on the first sign-in and reuses the issued client ID (never the `dynamic_agent_client` entrypoint), keeps a stable host ID beside `auth.json`, sends the saved ID token as the next sign-in's hint, and checks the ID token against the JWKS its OpenID configuration names before replacing a different account's credentials), `credentials` reads the store on every call and refreshes a token about to run out (one refresh at a time across clones, so a process keeps one handle and clones it), `logout` revokes the refresh token (network errors and 5xx tried again), clears the tokens either way and returns `SignedOut::Unconfirmed` when OpenAI did not confirm, `connected` says whether there are tokens with a client ID (a login from the old Codex flow, or one whose refresh token OpenAI has revoked, asks to sign in again). Depends on nothing else in the workspace.
- **nth-tools**: one module per tool (`read`, `write`, `edit`, `apply_patch`, `bash`, `glob`, `grep`, `webfetch`, `websearch`, `skill`, `question`, `panel`, `show_user`, `monitor`, `worktree`); `nth_tools::all()` lists them. A path the model names goes through `path::resolve`, which reads a leading `~` as the home directory through `nth_context::expand_home`, the one `~` rule the config and `/add-dir` share. `read` shows a PNG, JPEG, GIF or WebP to the model instead of reading it as text (`read/image.rs`): its size read from the header first and refused past 50 megapixels (a file past 64 MiB before it is read), then scaled to fit 1920 px and shrunk by quarters to fit `MAX_IMAGE_BYTES`, a re-encoded JPEG or WebP going out as a JPEG, a GIF as a PNG and an animation as its first frame, kept under its hash in `ToolContext.images` (the session's folder, `Store::images_dir` under `Store::images`; the front-ends set it each turn and a subagent shares its parent's) and put on `ToolContext.attachments`, or refused when `ToolContext.takes_images` is off or there is no folder. Any other file is read on a blocking thread only as far as its window needs (each line kept only up to its cut), the rest of its lines counted without being kept so the hint names its length, never past `MAX_TEXT_BYTES` (64 MiB) in (past that the hint says `of more than`); a FIFO, socket or device is refused, and opened non-blocking so one swapped in after the check cannot hang the call. `panel` shows chat, context, diagnostics, plan or work. The main-session `context` tool (`context_preview.rs`) inspects the latest logical request snapshot, the typed `Preview` (the first call of a turn without a front-end watching finds none and asks for one): its overview has budget and entry/tool metadata, and an `entry` index or `tool` name returns one full detail; indices can change with a new snapshot. `show_user` sends a file through the `Screen` on `ToolContext` (`Show::File`, an absolute path) and the TUI opens it in a tab. `worktree` is `enter_worktree`, which opens `.nth/worktrees/<name>` through nth-worktree and moves the session there (running the project's `.nth/worktree-setup` in a worktree it just created, `worktree/setup.rs`), and `exit_worktree`, which moves it back; both refuse in plan mode, since the plan file lives under the working directory. `question` reaches you through the `Asker` on `ToolContext`; a front-end without one (`nth run`) has nobody to ask, so the model decides. `bash` passes the model's commands (not yours) through `rtk rewrite` when rtk is on PATH and `[tools.bash] rtk` is on (`bash/rtk.rs`), running what it returns and noting it in the result. bash and the worktree setup script wait for their command through `process::run_to_exit`, which hands the output to a `Receiver` as it arrives (bash streams all of it to the front-end), keeps only a `Tail` of it for the model (the last `max_output_chars` times four bytes, so a chatty command never sits whole in memory) and kills the command's group on any end but its exit, disarming the guard only once bash is reaped. Every waiting tool names its argument `timeout_ms` in milliseconds and rejects `timeout`/`timeout_secs`; `command_output.rs` strips ANSI escapes from command output, and only that, before it reaches the model or the TUI. `grep` and `glob` walk on a blocking thread through `blocking::run`, whose `Stop` a guard in the call's future sets when the session loop drops it (cancel or the ceiling), so the walk, which checks it on every entry, ends with the call and no task watches for it; grep skips a file over 10 MiB and stops after 50,000 files or 10,000 matches, glob after 50,000 matches, each saying so in its result. `webfetch` allows loopback and private/LAN addresses but blocks link-local and cloud metadata hosts at the URL, every redirect and every resolved address, following at most ten redirects itself; it ignores `HTTP(S)_PROXY`, so a proxy cannot bypass that guard. `monitor` leaves a command running in a detached task (`process.rs` is what it shares with bash: `shell` also sets `AGENT=1`, `AI_AGENT=nth` and `AGENT_BROWSER_SESSION` to the session's id, so every command of a session drives one browser and parallel sessions never share one) and reports through `Monitors` on `ToolContext` to the front-end, which puts its stdout lines in the `Inbox` as notices for the model, while stdout and stderr both count toward the flood guard (a line ends at `\n` or `\r\n` and is cut at `MAX_LINE_BYTES`; a lone `\r` redraws it, so a progress bar collapses to its latest state in one line instead of tripping the guard, sent when the line or the watch ends; the inbox cuts a notice line at `NOTICE_LINE_CHARS`); without a front-end it refuses. `PostWrite` is what every file-writing tool goes through: `lock` takes the set of path identities (canonical where they exist, sorted, so overlapping patches cannot deadlock and different files run in parallel) and holds them while the tool reads, writes and formats each file through them; once they are dropped the tool asks the language servers about the file and returns the format note and their errors for the model. `apply_patch` validates every section before writing and, when a write fails, names the completed and unattempted operations and warns that the failing target may be partial. Read shares its `Lsp` and touches each file it reads without waiting, so the server is warm by the time the model writes.
- **nth-session**: `Session` (serializable history, model, effort, mode, cwd, and an unsaved `Context` that goes into the system prompt; `Session::size_to` is the one place a session is sized to its model from a `Listing`: limits, `takes_images`, cost, and its subagent and clerk llms through `SubagentLlm::sized`, called by `nth run` and the TUI's `adopt_llm` once the model is final), `Store` (one JSON file per session under `$XDG_DATA_HOME/nth/sessions`, saved after every turn, behind `/resume` and `nth -c`; loading reads back the bytes of the images its tool results name after the last compaction, which the save leaves out, only from files under `Store::images` whose hash matches, one copy per hash; `Store::monitor_dir` beside them holds the session's monitor logs, which `nth session delete` removes with it) and `Turn::run`, the agent loop: stream a reply, run its tool calls in parallel (their arguments first mended against the tool's schema, `agent_loop/repair.rs`: `"20"` for an integer, an object sent as a JSON string), feed results back, repeat until the model answers without tools (capped at `MAX_STEPS`). A call still running after `ToolContext.tool_timeout` (`Session.tool_timeout`, from `[session] tool_timeout_secs`, which subagents inherit) is dropped by `run_call` as cancel drops it and answered as timed out, except the tools in `tool_names::UNTIMED`, which wait for you or for a subagent with a budget of its own; `Session::shell` runs your `!` commands without the ceiling. `compaction/` keeps a long session inside the model's window: what is summarized and kept (`mod.rs`), `Turn::compact` running the summary request (`turn.rs`), and the messages a request carries once the history holds a compaction marker (`view.rs`). A tool that moved the working directory (`Workdir`) moves the turn's later steps and `run_call` sends `Event::Moved`, which the front-ends follow at once (the TUI's status bar, git state and file index); the session takes it on when the turn ends (`Session::set_cwd`, with `origin` the directory it left). `inbox/` is the model's `Inbox`: what it has not heard yet — monitor output the front-end posts, subagent answers and stalls, work item changes, Curios feedback, and prompts sent mid-turn — and `inbox/notice.rs`, the notice text that carries it, kept together with its parser (`split_notices`, which the transcript reads back); `instructions_notice` is the `<instructions>` element for an instruction file that changed, a unified diff when shorter than the file. The notice types sit beside their features (`subagent/notice.rs`: `TaskNotice`, `TaskOutcome`, `TaskStall`; `work/notice.rs`: `WorkNotice`, `WorkState`, `Todo`, `WorkOutcome`). `FrontEnd` (`front_end.rs`) is what a turn reaches the front-end through: the tool handles it passes on to `ToolContext` (`Asker`, `Screen`, `Monitors`, `ContextPreview`) and the `Inbox`, which only the turn reads (`Turn.inbox`, from `Held`): no tool sees it through `ToolContext`, and the tools that post to it, `Task` and `Work`, are built with it, so the front-end's one must be the one they hold (`nth`'s runtime makes one per process and hands it to the tools and, on `PreparedRuntime`, to the chat; headless it is `Inbox::default()`, which reaches no model, so they wait). A prompt sent mid-turn (`Inbox::take_prompts`) pre-empts a reply's tool calls: they are answered as interrupted and the turn goes on with your message. An instruction file that changed since the model read it (`ToolContext.watch`, the session's `Watch`) goes in front of the next prompt and between steps, the system prompt kept as it was so its cache holds. Between steps it hands the model what else the `Inbox` holds (`Inbox::take_notices`, then any prompts sent while the tools ran) as a user message. `Session.agent` is the primary agent the session runs as in place of its `mode` (`Session::primary`, `None` when the agent is gone): its prompt replaces the model's persona in the system prompt (memory, skills and agents stay), `ToolContext.agent` limits the tools the turn offers to those it `allows`, its tools write as in act, and `primary/` tells the model when it enters or leaves one mid-conversation (no plan reminders while one runs). `plan/` is plan mode: the plan file's path (`.nth/plans/<id>.md`) and opencode's reminders, appended to the prompt on entering plan mode and on switching to act (`plan::reminder` decides which); in plan mode the `Writable` on `ToolContext` (`plan::writable`) lets write, edit and apply_patch touch the plan file, the memory folder and the current session's Curios source workspace. Your own session's system prompt carries the memory section (`prompts/system/memory.md`: how to save, then the index); the model saves with write and edit, no memory tool, and `memory::ensure_dir` gives the folder a `.gitignore` of `*` before each turn in a repository. A subagent never sees or writes it. `usage` is what the session spent: a `Ledger` of one `Spend` per turn (model, steps, the tokens the provider reported — input, output, the cache counts and the reasoning share of the output — the model's `Cost` rates when the front-end's listing gave them, and a `ToolUse` per tool the turn called: calls, failures, time and output), counted by `Turn::run` as each request reports its usage and saved with the session; a spend prices at its stored rates, so `nth usage` works without a listing; a subagent's finished turn goes to `Subagents::take_spent`, and the front-end records it in the parent's ledger. Progress goes out as `Event`s over an `mpsc` channel; cancellation is a `CancellationToken` and always leaves `messages` valid to continue from. `subagent/` runs the agents nth-context found: `Subagents` is the registry (one actor task per subagent, owning its `Session` and taking prompts from an inbox one after another, reporting `SubagentEvent`s to the front-end), `Task` is the tool the model starts or continues one with (with an `Inbox` it returns at once and the answer lands there as a `<task>` notice; headless it waits), `Spawner` (`spawn.rs`) is how it and `work_assign` start one, on the parent's provider with its share of the tools and an agent's own `model` qualified by it, and `mention::resolve` turns `@name` in a prompt into opencode's instruction to call it. `work/` is the orchestration: a plan of serial cycles of parallel items under `.nth/work/<session>/` (`store.rs`: a numbered folder per cycle, one markdown file per item with its state in the frontmatter and its brief, `## Todo` and `## Result` in the body), written and read through `work_item`, `work_close` and `work_status`. `work_assign` puts a subagent on an item (only in the first cycle with an item not yet closed) with the item as its whole prompt (`assigned.md`) and one extra tool, `work_todo`, bound to that item through an `Assignment` that never holds `Work` or `Subagents` (a subagent holding its own registry would never end). The job's `Done::Work` returns the item file when the turn ends and posts `<work_item>` notices; the actor also reports a stall (`[work]` or `[task] stall_secs` without an event, and again while it stays silent) as a notice that replaces the last one and `SubagentEvent::Stalled`, which wakes the TUI. A turn past its budget is cancelled, and a cancelled turn (budget, stop or a front-end that is gone, which stops it at once) still running `actor::GRACE` later is dropped, its open calls answered as interrupted (`settle_unanswered`) and its job settled as timed out or interrupted; its spend so far stays, since a turn counts into a spend the ledger holds from the start (`Ledger::open`). Events reach the front-end through an outbox, so a front-end that falls behind never stops those clocks. `ToolContext.session` names the session a call runs for, which is how the tools find the plan; it lives under the main checkout (`work::root`, the `Workdir` origin), never under a worktree the session moved into. Todo ticks never wake the model on their own (`Inbox::wakes`): they ride along with a return or a stall, or go between steps. Every change to an item file is made holding `Files`, the lock that also knows which items a subagent of this process runs; an item a gone run of nth left `running` is settled as interrupted on the next work tool call. A subagent's session has `subagent` set and `parent` the session that started it (whose id its requests carry, `Request::parent_session_id`): its system prompt carries the agent's prompt instead of the model's persona and no agents list, and it never gets `task`, `question`, `panel`, `show_user` or `monitor`, nor the worktree tools unless its agent's own tool list names them (`task::OPT_IN`, `Agent::names`: the experimenter's), since entering one moves only the child's session. `curios/` is the session's side of Curios and the rules a front-end delivers its feedback and opens curios by. `session.rs` holds the `Session` methods: `curio_store` (at the saved `curio_root`, else `Store::open` from the state root; none for a subagent), `prepare_curios`, `deliver_curios` (feedback alone starts a turn, never parsed as a prompt), `acknowledge_curios` (after a save) and `Receipts`, through which a turn records each `CurioNotice` (`notice.rs`) in the step that puts it in the history; `curio_root` is kept from the store plan mode readies before a turn, else found (without building the store) once a main-session turn ends, so deletion and acknowledgment find what the tools made. The rest is all sync; `Poll::run`, `resolve` and `Stores::get` build stores and belong on a blocking thread, while `Delivery` runs on the front-end's loop: `Delivery` (`delivery.rs`) keeps the session's delivery lease and when to retry a refused claim (`CLAIM_RETRY`, telling once that another process delivers) or a failed acknowledgment, a `Poll` reads on a blocking thread and `Delivery::apply` turns what it read into `Polled` (feedback to post, a recorded batch the store still holds to catch up without waking the model); `fresh` is the dedup against the session's receipts, since `CurioDelivery::poll` (the lease, `delivery.rs`) only reads; `resolve` (`open.rs`) decides whose store serves an opened curio (`How`: its own, adopted from an idle session, or a running one's, which keeps it), and `Stores` caches one store per session id for a run.
  `context_preview.rs` projects the logical next request without changing the session or inbox: the effective post-compaction messages, the loop's offered tool definitions, pending items and an estimated budget (serialized bytes / 4 plus 2,500 tokens per image, not provider accounting). It excludes the unsent prompt. During a turn, the loop publishes main-session snapshots into `nth-protocol::ContextPreview` once at each committed boundary, a `Phase` (`PendingReply` before a request, `PendingResults` before its calls run, `Ready` after the results and the hand-over, `CompactionRequired`, and `Idle` when the turn or `/compact` ends), never streaming fragments, and builds none unless the slot `builds()`; it never stats instruction files, since the hand-over delivers their changes before the next step's request (only the idle preview shows one still pending).
- **nth-config**: `Config` and its sections (`lib.rs`), what `config.toml` and a repository's `.nth/config` hold, every key optional and unknown ones refused; `TEMPLATE` is the `nth init` template (`config.toml`), and tests keep it, the defaults and the internal `config` skill's reference agreeing. `layers.rs` layers the global file (`Config::default_path` in `Paths`' config directory, or `--config`) and the repository's (`repo_config`: the main checkout's in Git, else the nearest from the working directory up to home) into one: a repository may set only the allow-listed sections (`read_layer`), its `skills.paths` and `directories.paths` resolved component by component through symlinks (`resolve_path`, dangling links followed, a loop an error) and refused outside its root (`paths_inside`), and those two lists append while everything else merges as tables. `Config::load_in` takes the `Paths` to read from, so tests never touch the real home. `selection.rs` is `Selection`, what every kind of turn runs on and the one copy of its rules, plain data with no provider: `Slots` (plan, act, and the optional subagent and clerk), the mode and the primary agent running in its place (`pub` fields), each agent's model for the run (`set_agent`: what it was pinned on — picked by hand, act picked while it runs, or left on — else its own model at act's effort, else act's, which a profile cycle moves along with act until then), `current` (the agent's, else the mode's), `llm(Target)` (subagents fall back to the current, the clerk to the subagents'), the qualified `Profile`s and `next_profile`, which returns `Cycled` for the front-end to say. `Selection::from_config` builds it with the provider's `qualify` and `check` passed in as closures (`nth/src/runtime/llms.rs`), from the helpers on `Config` (`profile_llm`, `profile_subagent`, `profile_clerk`); `needs_model` says when a random model fills `model` first. `Target` (plan, act, agent, subagent, clerk) is what the model picker's Tab cycles. Both front-ends read it: the `nth` crate loads it, and the TUI reads its own sections off the `PreparedRuntime`.
- **nth-tui**: the interactive chat (ratatui + crossterm).
- **nth**: the clap CLI; with no subcommand it opens the TUI, `run` prints events with `render.rs`. `runtime/` is the one way a session starts, for the chat (at start and on `/resume`, through `Runtime::reload`, the TUI's `Reload`), `nth run` and `nth context`: `Runtime` keeps the config path, `--model`, the global directories (`Paths`, read from the environment once; the config's loading, `prepare` and the login take theirs from them, so tests point them at a temporary folder) and the process's one `nth_auth::ChatGpt` (`Runtime::chatgpt`, built on first use; the providers' endpoint, `/connect`, every `/resume` and `nth connect` take clones of it, so one token is refreshed once), `Runtime::config_for` loads the config for where a `Start` (`Fresh` or `Saved`) runs, `Runtime::providers` builds the providers from it (`nth context` passes offline ones), and `Runtime::prepare` returns the `nth_tui::PreparedRuntime`: the session with its context, qualified model, directories, limits and compaction, a model picked when the config names none (a warning), each mode's llm with a saved session's on its mode, the profiles, the one tool list (`runtime/tools.rs`, the task tool included), the shell and the config itself, which `prepare` takes by value and hands on. `config.rs` is only `nth config` and `nth init`, over `Runtime::config_file` and `Runtime::env`; `nth skills` and `nth agents` read `Runtime::paths`, so these commands take the global directories only from the `Runtime` (the session store, `Store::open`, and the TUI's `HOME` still read the environment). `nth run` sizes the session from a listing once its `--agent` switch makes the model final.

Front-ends only consume `Event`s; they never reach into the loop. The TUI moves the `Session` into a task for each turn and takes it back when the turn ends (`app/turn/`), so Esc cancels cooperatively rather than aborting the task; quitting mid-turn does the same and waits for the turn to save (`app/quit.rs`).

### TUI

`App` (`crates/nth-tui/src/app/mod.rs`) runs one `tokio::select!` loop over terminal input, session events, the running turn and background jobs, redrawing on every step. `App::new` takes the `PreparedRuntime` the chat starts on and installs it through `App::install`, as `/resume` does with the one its `Reload` prepares, so the two cannot drift. Installing takes the config's `[chat]`, `[layout]` and `[notify]` (`App::apply_config`): a section that changed since the last runtime's replaces the `/settings` toggles, the split width or the notifier, one that did not leaves them, so this run's `/settings` flips outlive a `/resume` whose config says the same; `/resume` then lists the new provider's models at once, so the status bar and the next turn's sizing need no `/models`. Each view's wiring in `app/` is the file named after it (`app/plan.rs` for `plan/`, `app/llm_picker.rs` for `llm_picker/`, `app/question.rs` for `question/`).

The screen is three bands, named as in `docs/ui.md`. Use these names in code and comments:

- **Content panel**: what you look at. `Content` (`app/content.rs`) holds the open tabs, shown in the header, and which one shows; a `Tab` is `Chat` (always first, never closed; until anything is said it shows `hero.rs`, a procedural ASCII field that moves on every tick and ripples under the mouse), `Diagnostics` (`diagnostics.rs`, wired by `app/diagnostics.rs`, including PATH checks for `tea` and `gh`), `Context` (`/context`, `context.rs`, wired by `app/context.rs`: the main session's scrollable next-request preview, kept with the `ContextPreview` the app hands each turn and the running turn's receiver in `ContextTab`; while visible and idle it is rebuilt from a cloned session at once on your changes (the turn ending, the tab opening or showing, a model, effort, mode, agent or `/add-dir` change, resume or a fresh session), while what arrives per line or per event (a monitor's stdout or end, a subagent's answer or stall, a work item's todo tick, a curio batch, a new listing, the terminal regaining focus) only marks it stale and the one-second tick rebuilds it once, as it does a tab that came into view without input (a resize that splits the panel, a tab closing by itself); while open it follows a running turn's snapshots, subscribed when the turn starts or the tab opens mid-turn (showing what the turn published so far, or waiting for its next step) and dropped when either ends), `File(id)` (`file.rs`: a file the `show_user` tool showed, as markdown or highlighted code, with a watcher task that polls it and sends it again whenever it changes; `app/file.rs` wires them, one tab per path, closed only by you), `Usage` (`usage.rs`: what the session spent, from `Spent` in `app/usage.rs`, the app's running ledger fed by the same usage reports the session counts, subagents' included; its all-time section also reads every saved session's tool totals, `App::load_tools`), `Work` (`work.rs`: the work plan as a tree from `nth_session::work::outline`, which `nth work` draws too; a running item's time and calls come from its subagent's tab, found by its description `work <item>`, and a running item with none is lost; `app/work.rs` reads it after every `work_*` call, a subagent's turn end and the end of each turn), `Plan` (`plan/`: the plan file with the latest turn's changes marked, opened while the file exists, dismissable, and shown again by `/plan` or the next revision; `app/plan.rs` reads it and runs `/approve`; `app/editor.rs` is ctrl+g, which hands the terminal to your editor on a copy of the plan while its tab shows — its diff goes to the model as review feedback, `nth_session::plan::edits` — or of the prompt, whose edits become its text again) or `Keymaps` (`keymaps.rs`: the read-only keyboard reference `/keymaps` opens, scrollable and closed only by you) or `Monitor(id)` (`monitor.rs`, one per running command, closable only once stopped; `app/monitor.rs` wires them and puts each one's stdout lines and end in the inbox as it hears them, never those of a monitor started for a session that was left, `MonitorTabs::forgotten`, and logs them under `Store::monitor_dir`) or `Subagent(id)` (`subagent.rs`: a header and the subagent's own `Chat`; `app/subagent.rs` wires them, and while one shows the prompt talks to it: its label names the agent, Enter queues into its inbox, Esc stops its turn), and later ones (Diff) become new variants. From `[layout] split_width` columns, once another tab is open, the panel splits (`Content::panes`): chat on the left, and on the right the last other tab that had the focus (`side`). The focus stays `Content::active`; hovering a pane moves it there. The `panel` tool switches tabs through the `Screen` on `ToolContext`, and `show_user` opens file tabs through it.
- **Input panel**: what you type into. The `Input` enum (`app/input.rs`) picks it: `Input::Prompt` by default, or a widget such as the model picker that swaps in and hands back to the prompt. `/settings` swaps in `settings/`: `ChatSettings` (show thinking, show tool output) starts from the `[chat]` table in the config, lives on `App` for this run only (`/settings` flips it, never writing back; a `/resume` onto a changed `[chat]` starts it over) and every `Chat::draw` lays its transcript out with it. `/connect` swaps in `connect/`: the providers that take an account (ChatGPT today) with a ✓ when connected, then, once Enter starts the browser login (`app/connect.rs`, a `Job` dropped by Esc), its URL to click or copy (`c`) while it waits; a login lists the models again and opens the model picker. `/memory` opens the memory index in a file tab. `/copy` copies the shown chat's latest completed answer as raw Markdown (a subagent's while its tab shows; the latest compaction summary counts as an answer) and `/copy-id` copies the session id. The model and session pickers filter as you type through `fuzzy.rs` (nucleo), as telescope does. `/` completes nth's commands and then the skills (`command/`); a skill runs by filling its template (`nth_context::skills::parse` and `Skill::invoke`), the same way `nth run "/name args"` does. `@` completes agents, then files (`mention/`), and one starting `../`, `./`, `/` or `~` browses the filesystem a directory at a time (`path.rs`, which `/add-dir` completes with too); a sent `@name` is resolved by the session (`nth_session::subagent::resolve`).
- **Mode**: Tab at the prompt switches plan and act (`app/mode.rs`); `App.selection` (nth-config's `Selection`) holds what every kind of turn runs on and is the one thing the prompt label, the status bar, the model picker, the diagnostics tab and each turn read, so nothing is synced on a switch. Each mode keeps its own model and effort (its `Slots`, from the active `[[profiles]]` entry in the config, or the `model` fallback when there are none). `Slots.subagent` is what subagents run on (a profile's `[profiles.subagent]`; `None` is the parent's model), handed to the session each turn as `Session::subagent_llm` and to `child_session` through `ToolContext.subagent`; an agent's own `model` still wins. `Slots.clerk` is what the built-in clerk runs on (`[profiles.clerk]`; `None` is the subagents' model), handed over the same way as `Session::clerk_llm` and `ToolContext.clerk`; only the built-in has `Agent::clerk` set, so a `clerk.md` replacing it runs as any other subagent. Tab in the model picker cycles its `Target` (plan, act, subagent, clerk), starting on the current mode, and the diagnostics tab shows a row for each of plan, act, subagent and clerk. `/agents` (`agent_picker/`, wired by `app/agent_picker.rs`) runs later turns as a primary agent in place of the mode: `selection.agent`, handed to the session each turn as `Session::agent`, on its own model for this run (`Selection::set_agent`: what it was pinned on — picked by hand, act picked while it runs, or left on — else its `model`, qualified through `Provider::qualify` by `App::set_agent`, at act's effort, else act's), which the model picker reaches as `Target::Agent` while one runs; Tab (`App::toggle_mode`) goes back to the mode, and the prompt's label names the agent in `AGENT_COLOUR`. `app/profiles.rs` cycles the profiles with ctrl+p through `Selection::next_profile` (skipping ones whose provider has no key, or that run on ChatGPT while it is not connected, asked on every cycle so a `/connect` counts) and says the `Cycled` it returns; a model picked by hand for any slot leaves the profile, and the next ctrl+p restores it. The chat takes the `Selection` its runtime prepared, on start and on a `/resume` that prepares another (one that does not keeps the current), put on the session's mode, agent and model (`mode::follow`).
- **Commands**: `!` at the start of the prompt makes it a command (`Prompt::shell`, label `cmd` in yellow). Enter runs it through `Session::shell` on the untimed `Bash` the `PreparedRuntime` hands over, as a turn without the model (`App::start_shell`); the session records it as opencode does, `SHELL_PROMPT` then a bash call and its result.
- **Mouse** (`app/mouse.rs`): the wheel scrolls the showing tab, a click on the header shows that tab (`header::tab_areas`), a left click in a chat opens the link under it (`Chat::link_at`, from the links `rich::markdown` carries through wrapping) and a right click copies the entry under it (`Entry::clipboard`, through `terminal::copy`, OSC 52), or the status bar's working directory or branch. Each chat records where its last draw put it, so clicks in a subagent's tab work the same. What the pointer is over is a `Target`: the draw records each one with `Areas::target` (a popup over the panes with `Areas::cover`), a chat's links and entries are looked up live, and `App::draw_hover` marks every hit last, so two can show at once: a header tab or chat link turns `theme::HOVER` (magenta), a status bar link `theme::HOVER_STATUS` (white), and a chat entry gets `theme::HOVER_ENTRY` (dark grey) behind it, only where nothing set a background, so hoodrich's code blocks keep theirs. Something new to point at is a `Target` variant, one `Areas::target` call where it is drawn and an arm in `App::click` or `App::right_click`.
- **Status bar**: always `status::ROWS` (2) lines at the bottom.

Heights are decided bottom-up: the status bar, then the input panel's own `Input::rows()`, then the content panel takes the rest. A view's state lives on `App` (`App.chat`, `App.prompt`), not in the enum variant, so it keeps up with the session and keeps its text while hidden. A tab with state beyond its view keeps it together in one struct in its wiring file (`FileTabs` in `app/file.rs`, `WorkTab`, `PlanTab`): the view, what it reads and its background job, with a `next()` the loop's `select!` waits on that resolves with the job's result.

Markdown and code go through `rich.rs`, the only module that uses [hoodrich](https://github.com/kloki/hoodrich). Chat messages are concealed markdown. read, write, edit (as a diff) and webfetch output are highlighted by tool (`output_lines` in `chat/render.rs`). The plan tab renders the plan as markdown. hoodrich gives one line per source line, and `rich::wrap` wraps them with their styles kept, because every pane draws pre-wrapped lines. Every tab uses a `Pager` (`pager.rs`) for scrolling, which the keys and wheel move; Home and End scroll the active content to the top and bottom; a monitor's follows the newest line, and the file and plan tabs keep their wrapped lines in a `Cache` until they or the width change. A chat uses the same pager with half-screen pages and draws only a window of its transcript.

Completion notifications (`app/notify.rs`) are suppressed while subagents or monitors run or the inbox has wakeable notices; questions and failures still notify. A plan-mode completion waits for the plan read before deciding which notification to send.

TUI tests render `App` into a `TestBackend` and assert on rows (`rows()` in `app/tests/mod.rs`), so layout changes mean updating row indexes there. Turns in tests run against one fake provider, `Scripted` (`app/tests/provider.rs`): a script of replies (events, a failure, a hang, or events once a gate opens), then a fallback for every later request.

Style: no borders or divider lines; bands differ by background and spacing. Use only the 16 ANSI colours plus the terminal's default foreground and background, never hex or RGB (see `docs/ui.md`). The one exception is syntax-highlighted code, which hoodrich draws in Dracula colours.

## opencode reference

`refs/opencode` is a gitignored local clone of opencode pinned to the commit named in `docs/research/opencode/README.md`. The `research-opencode` skill in `.claude/skills/` studies it and writes notes under `docs/research/opencode/`; the `opencode-changes` skill reviews what opencode changed since the pin (each feature linked to its commit, with a verdict on adopting it) under `docs/research/opencode/changes/`, then moves the pin.
