# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

nth ("N-th time") is a personal, opinionated coding harness in Rust: a cargo workspace that builds one `nth` binary. `docs/design.md` is the design doc, `docs/ui.md` the TUI layout spec, and `docs/todo.md` lists what opencode has that nth does not yet (a reference, not a backlog).

## Commands

CI runs these three, and all must pass:

```sh
cargo test --workspace
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
```

- Single test: `cargo test -p nth-tui prompt_and_status_rows_never_move` (any substring of the test path works).
- Run the TUI: `cargo run -p nth`. It needs at least one usable provider: ChatGPT is built in and runs once `nth connect` signs in to your subscription; otherwise run `nth init` and uncomment one, with its API key set (OpenCode Go and Zen read `OPENCODE_API_KEY`). `NTH_MODEL` (or `--model`) picks the model as `provider/model`; with none set, a random one the providers list is used.
- Headless: `cargo run -p nth -- run "<prompt>"` (act mode; `--mode plan` to plan). List models: `cargo run -p nth -- models`. List skills: `cargo run -p nth -- skills`. List agents: `cargo run -p nth -- agents`. List formatters: `cargo run -p nth -- formatters`. List language servers: `cargo run -p nth -- lsp`; what they say about a file: `cargo run -p nth -- lsp diagnostics <file>`. Send a sample desktop notification: `cargo run -p nth -- notify` (`--event needs-you` and others). What a saved session spent: `cargo run -p nth -- usage [<id>]` (`--all` per day and model, `--json`). Its work plan: `cargo run -p nth -- work [<id>]` (`--json`). The saved sessions of this directory (those that moved from it into a worktree too), newest first: `cargo run -p nth -- session list` (`-n <count>`, `--all` for every directory, `--json`); delete one with its plan, work items, monitor logs and images: `cargo run -p nth -- session delete <id>` (any start of the id; `/copy-id` in the TUI copies it). Sign in to ChatGPT in the browser: `cargo run -p nth -- connect` (`--status`, with `--json`; `--logout`).
- Config: optional `~/.config/nth/config.toml` (or `--config`, `NTH_CONFIG`); `cargo run -p nth -- init` writes one with every key and its default (`--force` to overwrite; the template, `crates/nth/src/config.toml`, is the reference for every key, and has OpenCode Go and Zen commented out), and `cargo run -p nth -- config` prints the resolved one. Flags and env vars win over it. Another provider is a `[provider.<id>]` block with `base_url` and `api_key_env`; the id `chatgpt` is reserved for the built-in one.
- A new config key goes into the `nth init` template (`crates/nth/src/config.toml`, with its default and a comment) and into the internal `config` skill (`crates/nth-context/src/skills/internal/config/SKILL.md`) in the same change, so both keep listing every key.

## Architecture

Crates in `crates/`, from the bottom up:

- **nth-context**: what nth reads about a project before the first prompt: instruction files (`AGENTS.md`, or `CLAUDE.md` where a project has none), skills (`SKILL.md` folders in the Claude Code, opencode, open-standard and nth places, plus the internal ones nth ships in `skills/internal/` (`init`, opencode's `AGENTS.md` setup; `setup-worktrees`, which writes `.nth/worktree-setup`; `work-plan`; `config`, how to set up `config.toml`; `browser`, which drives a browser with the agent-browser CLI through bash; `screenshot`, which captures the screen, a window or a region with the platform's CLI and reads the file), which a skill file of the same name replaces) and agents (`agents/`: opencode's built-in `general` and `explore`, nth's `clerk` for small one-off tasks such as a commit message, plus one markdown file per agent in the Claude Code, opencode and nth places, the body being its system prompt), found by `Context::discover`, the instruction walk going from the working directory up to the home directory when under it, else to the project root, and the nested ones the read tool attaches (`instructions::nested`, from the folder of a file read or a directory listed). `frontmatter` reads the YAML block skills and agents share. `Paths` carries the home and config directories so tests never touch the real ones. Depends on nothing else in the workspace.
- **nth-protocol**: types every crate shares: `Message`, `Event`, `Mode` (plan or act), and the `Provider` and `Tool` traits. Anything swappable sits behind one of these traits. It re-exports `nth_context::agents::tool_names` (`WRITERS`, `writes_files`, `touches_work`, `WORK_TODO`), the names that agent permissions, plan-mode subagents and the TUI decide on. `tool.rs` owns what a failed call leaves: `failed` writes the `Error: ` result, `failure_reason` reads the reason back (the usage ledger and the TUI do), and `INTERRUPTED` is the reason when you cut a call short. Also the handles a tool reaches the front-end through, bundled as `FrontEnd` on `ToolContext`: `Asker` (questions), `Screen` (which tab shows), `Monitors` (`monitor/`: the wire types and the registry of running commands) and `Attachments` (`image.rs`: the `Image`s a tool shows the model beside its text, one per call, which `run_call` puts on the `Message::ToolResult`; an image's bytes live in a file of their own, `path`, and ride along base64 in `data`, which is never saved) and `Inbox` (`inbox/`: what the model has not heard yet — monitor output, subagent answers, and prompts sent mid-turn, which pre-empt the turn's next tool calls — and the notice text that carries it, kept together with its parser). `Workdir` on `ToolContext` is where a tool moves the session's working directory (the worktree tools), shared by the calls of a turn.
- **nth-llm**: `Provider` impls. One module per wire protocol, each a `Client` that streams one request: `chat_completions` (OpenCode Go or any OpenAI-compatible endpoint, and what a model goes over when the catalogue says nothing else), `messages` (Anthropic messages, for Claude on Zen and MiniMax on Go) and `responses` (OpenAI responses, for GPT on Zen and GPT and Grok on Go). `providers/` is the one `Provider` the front-ends see: an `Endpoint` per `[provider.<id>]` in the config (`endpoint.rs`), each with its three clients, and `listing.rs` for its `/models` and the merged listing. An endpoint signs requests with its `Credentials` (`auth.rs`): an API key, or `ChatGpt` from nth-auth, resolved once per request (refreshing the token) and put on the wire by each client (for ChatGPT also `ChatGPT-Account-Id`, `originator` and `session-id`); a login that fails is a request error never retried. `chatgpt.rs` is the one built-in endpoint, `chatgpt`, on the Codex backend: always responses, OpenAI's catalogue entry for what a model needs on the wire, and its models from the backend's own list (`GET /models?client_version=`, which differs by plan and account: the listed, API-supported ones, with the backend's context window and efforts and the catalogue's output limit) at no price; the endpoint remembers the efforts its last list offered, and `stream` snaps a request's effort to those before the catalogue's. It is always among the endpoints but asked `connected()` each time: until then its models are refused (`providers::Error::Auth`) and it is left out of the listing, so connecting mid-run needs nothing rebuilt. A model id is `provider/model`: the prefix routes the request to its endpoint and the rest goes on the wire, and a bare id goes to the default provider (the config model's). `catalog` is models.dev, fetched once in the background when `Providers` is built (`Snapshot`), whose entry for an endpoint is the one with its `base_url` as `api`, else the one keyed by its config id (`provider_for`, so `[provider.openai]` finds OpenAI's); an endpoint with no entry borrows a model's name, limits and efforts from another provider's (`borrowed`: by id, else the part after the last `/`, preferring the `canonical_model_id`), never its price or wire. The listing reads names, limits and the efforts a model takes (`reasoning_options`) from it, and `stream` snaps the request's effort to the nearest of those and dispatches on the `Wire` its SDK for the model maps to, handing the protocol the catalogue's entry for what it needs (an output limit, whether the model reasons, adaptive thinking or a budget on messages). Whether a model takes images is the catalogue's `modalities.input` (`ModelInfo::takes_images`, `None` for a model it does not know, which is sent images; ChatGPT's from the backend's `input_modalities`), and `providers/images.rs` rewrites a request's images before it goes out: one whose file was gone at load, one over `MAX_IMAGE_BYTES` (Anthropic's 5 MB of base64), or any for a model that takes none, becomes a note in its result's text, and past 25 MiB or 50 images the oldest become the removal note down to 15 MiB, never those of the latest run of results unless they alone are too many. messages and responses carry a tool result's images inside it; chat completions sends them in one user message after a run of results, since some servers take only text in a `tool` message. A model it does not know, or no catalogue at all, goes over chat completions; one whose protocol nth does not speak (Gemini's) is not listed. A chat completions request carries the session id as `prompt_cache_key` only for a provider on its allowlist of models.dev ids (`chat_completions::takes_cache_key`, asked through `Endpoint::takes_cache_key`), since strict servers refuse unknown fields. `http` is what the protocols share on the wire: the one `reqwest` client, the user agent, the session headers (`x-opencode-session`, `x-opencode-session-id` and, for a subagent, `x-opencode-parent-session-id`), the deadlines and the HTTP facts that decide a retry; `sse` is the line splitting and the `Parser` their streams share, each protocol's `event.rs` giving it the events one line holds.
- **nth-format**: the formatters run after a tool writes a file: opencode's built-in table (`registry.rs`), each with a probe for whether it applies to the project, plus custom ones from `[format]` in the config. `Formatters::format` runs every match; `nth formatters` prints `Formatters::status`.
- **nth-lsp**: language server diagnostics, LSP written by hand (`transport`, `types`, `client/`). `server/` is opencode's server table (rust-analyzer, typescript-language-server, gopls, pyright and more, used only when on PATH) plus `[lsp]` from the config, with the project-root rules. `Lsp` is one process-wide, cheap-to-clone pool: `touch(path, wait)` starts a client per (server, root) on first use (stopped again once untouched for `[lsp] idle_secs`) and returns the diagnostics, `status()` is a `watch` of every client's state, and `report` writes opencode's text for the model. `nth lsp` prints `Lsp::servers_for`.
- **nth-notify**: desktop notifications. `Event::notification` fills the texts in `templates/` from a `Context` (session title, elapsed, last reply); a `Backend` shows them (`notify_send.rs` on Linux, `osascript.rs` on macOS, the platform's by default; `[notify]` picks one via `BackendKind`), and `Notifier` is the cheap-to-clone handle a front-end sends through without waiting. Depends on nothing else in the workspace.
- **nth-icons**: every icon nth draws, as one set (`PLAIN`: Unicode any font has, each icon one column wide) that the TUI and CLI read through `icons()`. A new icon is a field on `Icons`, never a literal at the call site. Depends on nothing else in the workspace.
- **nth-worktree**: git worktrees under `.nth/worktrees` in the main checkout, one per name and on the branch of that name: `open` makes one on first use (the folder ignored by its own `.gitignore`), `changes` says what it has beyond a commit, `remove` deletes it with its branch. Depends on nothing else in the workspace.
- **nth-auth**: signing in to providers that take an account rather than an API key. `Store` is `auth.json` in the data directory (opencode's shape, one entry per provider id, written aside and renamed over with mode 0600). `ChatGpt` is a ChatGPT subscription signed in to as the Codex CLI is: `login` runs OAuth with PKCE in the browser (a callback server on `localhost:1455` written by hand, the pages in `templates/`), `credentials` reads the store on every call and refreshes a token about to run out (one refresh at a time across clones), `connected` says whether there are tokens. Depends on nothing else in the workspace.
- **nth-tools**: one module per tool (`read`, `write`, `edit`, `apply_patch`, `bash`, `glob`, `grep`, `webfetch`, `websearch`, `skill`, `question`, `panel`, `show_user`, `monitor`, `worktree`); `nth_tools::all()` lists them. A path the model names goes through `path::resolve`, which reads a leading `~` as the home directory. `read` shows a PNG, JPEG, GIF or WebP to the model instead of reading it as text (`read/image.rs`): its size read from the header first and refused past 50 megapixels (a file past 64 MiB before it is read), then scaled to fit 1920 px and shrunk by quarters to fit `MAX_IMAGE_BYTES`, a re-encoded JPEG or WebP going out as a JPEG, a GIF as a PNG and an animation as its first frame, kept under its hash in `ToolContext.images` (the session's folder, `Store::images_dir` under `Store::images`; the front-ends set it each turn and a subagent shares its parent's) and put on `ToolContext.attachments`, or refused when `ToolContext.takes_images` is off or there is no folder. `panel` shows chat, diagnostics, plan or work. `show_user` sends a file through the `Screen` on `ToolContext` (`Show::File`, an absolute path) and the TUI opens it in a tab. `worktree` is `enter_worktree`, which opens `.nth/worktrees/<name>` through nth-worktree and moves the session there (running the project's `.nth/worktree-setup` in a worktree it just created, `worktree/setup.rs`), and `exit_worktree`, which moves it back; both refuse in plan mode, since the plan file lives under the working directory. `question` reaches you through the `Asker` on `ToolContext`; a front-end without one (`nth run`) has nobody to ask, so the model decides. `bash` passes the model's commands (not yours) through `rtk rewrite` when rtk is on PATH and `[tools.bash] rtk` is on (`bash/rtk.rs`), running what it returns and noting it in the result. `monitor` leaves a command running in a detached task (`process.rs` is what it shares with bash: `shell` also sets `AGENT_BROWSER_SESSION` to the session's id, so every command of a session drives one browser and parallel sessions never share one) and reports through `Monitors` on `ToolContext`, which puts its stdout lines in the `Inbox` as notices for the model; without a front-end it refuses. `PostWrite` is what every file-writing tool calls after writing: it formats the file, asks the language servers about it, and returns the format note and their errors for the model. Read shares its `Lsp` and touches each file it reads without waiting, so the server is warm by the time the model writes.
- **nth-session**: `Session` (serializable history, model, effort, mode, cwd, and an unsaved `Context` that goes into the system prompt), `Store` (one JSON file per session under `$XDG_DATA_HOME/nth/sessions`, saved after every turn, behind `/resume` and `nth -c`; loading reads back the bytes of the images its tool results name after the last compaction, which the save leaves out, only from files under `Store::images` whose hash matches, one copy per hash) and `Turn::run`, the agent loop: stream a reply, run its tool calls in parallel (their arguments first mended against the tool's schema, `agent_loop/repair.rs`: `"20"` for an integer, an object sent as a JSON string), feed results back, repeat until the model answers without tools (capped at `MAX_STEPS`). A tool that moved the working directory (`Workdir`) moves the turn's later steps and `run_call` sends `Event::Moved`, which the front-ends follow at once (the TUI's status bar, git state and file index); the session takes it on when the turn ends (`Session::set_cwd`, with `origin` the directory it left). A prompt sent mid-turn (`Inbox::take_prompts`) pre-empts a reply's tool calls: they are answered as interrupted and the turn goes on with your message. Between steps it hands the model what else the `Inbox` holds (`Inbox::take_notices`, then any prompts sent while the tools ran) as a user message. `plan/` is plan mode: the plan file's path (`.nth/plans/<id>.md`) and opencode's reminders, appended to the prompt on entering plan mode and on switching to act; in plan mode the `Writable` on `ToolContext` lets write, edit and apply_patch touch only the plan file. `usage` is what the session spent: a `Ledger` of one `Spend` per turn (model, steps, the tokens the provider reported — input, output, the cache counts and the reasoning share of the output — the model's `Cost` rates when the front-end's listing gave them, and a `ToolUse` per tool the turn called: calls, failures, time and output), counted by `Turn::run` as each request reports its usage and saved with the session; a spend prices at its stored rates, so `nth usage` works without a listing; a subagent's finished turn goes to `Subagents::take_spent`, and the front-end records it in the parent's ledger. Progress goes out as `Event`s over an `mpsc` channel; cancellation is a `CancellationToken` and always leaves `messages` valid to continue from. `subagent/` runs the agents nth-context found: `Subagents` is the registry (one actor task per subagent, owning its `Session` and taking prompts from an inbox one after another, reporting `SubagentEvent`s to the front-end), `Task` is the tool the model starts or continues one with (with an `Inbox` it returns at once and the answer lands there as a `<task>` notice; headless it waits), and `mention::resolve` turns `@name` in a prompt into opencode's instruction to call it. `work/` is the orchestration: a plan of serial cycles of parallel items under `.nth/work/<session>/` (`store.rs`: a numbered folder per cycle, one markdown file per item with its state in the frontmatter and its brief, `## Todo` and `## Result` in the body), written and read through `work_item`, `work_close` and `work_status`. `work_assign` puts a subagent on an item (only in the first cycle with an item not yet closed) with the item as its whole prompt (`assigned.md`) and one extra tool, `work_todo`, bound to that item through an `Assignment` that never holds `Work` or `Subagents` (a subagent holding its own registry would never end). The job's `Done::Work` returns the item file when the turn ends and posts `<work_item>` notices; the actor also reports a stall (`[work] stall_secs` without an event) as a notice and `SubagentEvent::Stalled`, which wakes the TUI. `ToolContext.session` names the session a call runs for, which is how the tools find the plan; it lives under the main checkout (`work::root`, the `Workdir` origin), never under a worktree the session moved into. Todo ticks never wake the model on their own (`Inbox::wakes`): they ride along with a return or a stall, or go between steps. Every change to an item file is made holding `Files`, the lock that also knows which items a subagent of this process runs; an item a gone run of nth left `running` is settled as interrupted on the next work tool call. A subagent's session has `subagent` set and `parent` the session that started it (whose id its requests carry, `Request::parent_session_id`): its system prompt carries the agent's prompt instead of the model's persona and no agents list, and it never gets `task`, `question`, `panel`, `show_user`, `monitor` or the worktree tools.
- **nth-tui**: the interactive chat (ratatui + crossterm).
- **nth**: the clap CLI; with no subcommand it opens the TUI, `run` prints events with `render.rs`. `tools()` in `main.rs` builds the one tool list both front-ends use, the task tool included.

Front-ends only consume `Event`s; they never reach into the loop. The TUI moves the `Session` into a task for each turn and takes it back when the turn ends (`app/turn.rs`), so Esc cancels cooperatively rather than aborting the task.

### TUI

`App` (`crates/nth-tui/src/app/mod.rs`) runs one `tokio::select!` loop over terminal input, session events, the running turn and background jobs, redrawing on every step.

The screen is three bands, named as in `docs/ui.md`. Use these names in code and comments:

- **Content panel**: what you look at. `Content` (`app/content.rs`) holds the open tabs, shown in the header, and which one shows; a `Tab` is `Chat` (always first, never closed; until anything is said it shows `hero.rs`, a procedural ASCII field that moves on every tick and ripples under the mouse), `Diagnostics` (`diagnostics.rs`), `File(id)` (`file.rs`: a file the `show_user` tool showed, as markdown or highlighted code, with a watcher task that polls it and sends it again whenever it changes; `app/shown.rs` wires them, one tab per path, closed only by you), `Usage` (`usage.rs`: what the session spent, from `app/spent.rs`, the app's running ledger fed by the same usage reports the session counts, subagents' included; its all-time section also reads every saved session's tool totals, `App::load_tools`), `Work` (`work.rs`: the work plan as a tree from `nth_session::work::outline`, which `nth work` draws too; a running item's time and calls come from its subagent's tab, found by its description `work <item>`, and a running item with none is lost; `app/work.rs` reads it after every `work_*` call, a subagent's turn end and the end of each turn), `Plan` (`plan/`: the plan file with the latest turn's changes marked, opened while the file exists, dismissable, and shown again by `/plan` or the next revision; `app/plan.rs` reads it and runs `/approve`; `app/editor.rs` is ctrl+g, which hands the terminal to your editor on a copy of the plan while its tab shows — its diff goes to the model as review feedback, `nth_session::plan::edits` — or of the prompt, whose edits become its text again) or `Monitor(id)` (`monitor.rs`, one per running command, closable only once stopped; `app/monitor.rs` wires them) or `Subagent(id)` (`subagent.rs`: a header and the subagent's own `Chat`; `app/subagent.rs` wires them, and while one shows the prompt talks to it: its label names the agent, Enter queues into its inbox, Esc stops its turn), and later ones (Diff) become new variants. From `[layout] split_width` columns, once another tab is open, the panel splits (`Content::panes`): chat on the left, and on the right the last other tab that had the focus (`side`). The focus stays `Content::active`; hovering a pane moves it there. The `panel` tool switches tabs through the `Screen` on `ToolContext`, and `show_user` opens file tabs through it.
- **Input panel**: what you type into. The `Input` enum (`app/input.rs`) picks it: `Input::Prompt` by default, or a widget such as the model picker that swaps in and hands back to the prompt. `/settings` swaps in `settings/`: `ChatSettings` (show thinking, show tool output) starts from the `[chat]` table in the config, lives on `App` for this run only (`/settings` flips it, never writing back) and every `Chat::draw` lays its transcript out with it. `/connect` swaps in `connect/`: the providers that take an account (ChatGPT today) with a ✓ when connected, then, once Enter starts the browser login (`app/connect.rs`, a `Job` dropped by Esc), its URL to click or copy (`c`) while it waits; a login lists the models again and opens the model picker. The model and session pickers filter as you type through `fuzzy.rs` (nucleo), as telescope does. `/` completes nth's commands and then the skills (`command/`); a skill runs by filling its template (`nth_context::skills::parse` and `Skill::invoke`), the same way `nth run "/name args"` does. `@` completes agents, then files (`mention/`); a sent `@name` is resolved by the session (`nth_session::subagent::resolve`).
- **Mode**: Tab at the prompt switches plan and act (`app/mode.rs`); each mode keeps its own model and effort (`ModeLlms`, from the active `[[profiles]]` entry in the config, or the `model` fallback when there are none), and `App.model`/`App.effort` are the current mode's. `ModeLlms.subagent` is what subagents run on (a profile's `[profiles.subagent]`; `None` is the parent's model), handed to the session each turn as `Session::subagent_llm` and to `child_session` through `ToolContext.subagent`; an agent's own `model` still wins. `ModeLlms.clerk` is what the built-in clerk runs on (`[profiles.clerk]`; `None` is the subagents' model), handed over the same way as `Session::clerk_llm` and `ToolContext.clerk`; only the built-in has `Agent::clerk` set, so a `clerk.md` replacing it runs as any other subagent. Tab in the model picker cycles its `Target` (plan, act, subagent, clerk), starting on the current mode, and the diagnostics tab shows a row for each of plan, act, subagent and clerk. `app/profiles.rs` cycles the profiles with ctrl+p (skipping ones whose provider has no key, or that run on ChatGPT while it is not connected, asked on every cycle so a `/connect` counts); a model picked by hand leaves the profile for both modes, and the next ctrl+p restores it.
- **Commands**: `!` at the start of the prompt makes it a command (`Prompt::shell`, label `cmd` in yellow). Enter runs it through `Session::shell` on the untimed `Bash` that `nth_tui::Tools` hands over, as a turn without the model (`App::start_shell`); the session records it as opencode does, `SHELL_PROMPT` then a bash call and its result.
- **Mouse** (`app/mouse.rs`): the wheel scrolls the showing tab, a click on the header shows that tab (`header::tab_at`), a left click in a chat opens the link under it (`Chat::link_at`, from the links `rich::markdown` carries through wrapping) and a right click copies the entry under it (`Entry::clipboard`, through `terminal::copy`, OSC 52). Each chat records where its last draw put it, so clicks in a subagent's tab work the same.
- **Status bar**: always `status::ROWS` (2) lines at the bottom.

Heights are decided bottom-up: the status bar, then the input panel's own `Input::rows()`, then the content panel takes the rest. A view's state lives on `App` (`App.chat`, `App.prompt`), not in the enum variant, so it keeps up with the session and keeps its text while hidden.

Markdown and code go through `rich.rs`, the only module that uses [hoodrich](https://github.com/kloki/hoodrich). Chat messages are concealed markdown. read, write, edit (as a diff) and webfetch output are highlighted by tool (`output_lines` in `chat/render.rs`). The plan tab renders the plan as markdown. hoodrich gives one line per source line, and `rich::wrap` wraps them with their styles kept, because every pane draws pre-wrapped lines.

TUI tests render `App` into a `TestBackend` and assert on rows (`rows()` in `app/mod.rs` tests), so layout changes mean updating row indexes there.

Style: no borders or divider lines; bands differ by background and spacing. Use only the 16 ANSI colours plus the terminal's default foreground and background, never hex or RGB (see `docs/ui.md`). The one exception is syntax-highlighted code, which hoodrich draws in Dracula colours.

## opencode reference

`refs/opencode` is a gitignored local clone of opencode pinned to the commit named in `docs/research/opencode/README.md`. The `research-opencode` skill in `.claude/skills/` studies it and writes notes under `docs/research/opencode/`; the `opencode-changes` skill reviews what opencode changed since the pin (each feature linked to its commit, with a verdict on adopting it) under `docs/research/opencode/changes/`, then moves the pin.
