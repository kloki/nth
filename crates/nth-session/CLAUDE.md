# nth-session

Notes for working in this crate. The root `CLAUDE.md` has the commands, the crate map and the rules every crate keeps.

`Session` (serializable history, model, effort, mode, cwd, an unsaved `Context` that goes into the system prompt, and `env`, the unsaved `TurnEnv` a front-end sets in one assignment before each turn: the config's compaction policy, step limit and tool ceiling, whether the model takes images, its cost, the images folder and what its subagents and clerk run on, which `child_session` fills for a child from the parent's `ToolContext`; `Session::size_to` is the one place a session is sized to its model from a `Listing`: limits, `takes_images`, cost, and its subagent and clerk llms through `ModelSettings::sized`, called by `nth run` and the TUI's `adopt_llm` once the model is final), `Store` (one JSON file per session under `$XDG_DATA_HOME/nth/sessions`, saved after every turn, behind `/resume` and `nth -c`; loading reads back the bytes of the images its tool results name after the last compaction, which the save leaves out, only from files under `Store::images` whose hash matches, one copy per hash; `Store::monitor_dir` beside them holds the session's monitor logs; `Store::delete_session` removes the save with its plan, work folder, monitor logs, images and Curios folder (refusing a Curios root that is relative, traverses a parent or reaches it through a symlink, before anything goes; once the save is gone a folder that will not go is reported in `Deleted::failed` and the rest still go) and leaves its worktrees, behind `nth session delete`, which exits non-zero on such a failure) and `Turn::run`, the agent loop: stream a reply, run its tool calls in parallel (their arguments first mended against the tool's schema, `agent_loop/repair.rs`: `"20"` for an integer, an object sent as a JSON string), feed results back, repeat until the model answers without tools (capped at `MAX_STEPS`). Calls a guard answers without running them (the last step's under that cap, a doom loop's, those a prompt sent mid-turn pre-empts) go through `answer_unrun` (`agent_loop/call.rs`), which sends `ToolStarted` and `ToolFinished` for each as `run_call` does, so `nth run` prints the rows a replay of the session draws. A call still running after `ToolContext.tool_timeout` (`TurnEnv::tool_timeout`, from `[session] tool_timeout_secs`, which subagents inherit) is dropped by `run_call` as cancel drops it and answered as timed out, except the tools in `tool_names::UNTIMED`, which wait for you or for a subagent with a budget of its own; `Session::shell` runs your `!` commands without the ceiling, in the session's tool context for what bash reads (`tool_context`: the working directory, the session id, so one browser with the model's commands, the extra directories and the state root), its `SHELL_PROMPT` joining a prompt a failed turn left unanswered as the next prompt would (`push_user`). `session/` is `Session` split by what a reader looks for: the record, its builders and the system prompt (`mod.rs`), turn preparation, the tool context and manual compaction (`turn.rs`), and the shell (`shell.rs`); its Curios half is `curios/session.rs`. `compaction/` keeps a long session inside the model's window: what is summarized and kept (`mod.rs`), `Turn::compact` running the summary request (`turn.rs`), and the messages a request carries once the history holds a compaction marker (`view.rs`). A tool that moved the working directory (`Workdir`) moves the turn's later steps and `run_call` sends `Event::Moved`, which the front-ends follow at once (the TUI's status bar, git state and file index); the session takes it on when the turn ends (`Session::set_cwd`, with `origin` the directory it left). `inbox/` is the model's `Inbox`: what it has not heard yet — monitor output the front-end posts, subagent answers and stalls, work item changes, Curios feedback, and prompts sent mid-turn — and `inbox/notice.rs`, the notice text that carries it, kept together with its parser (`split_notices`, which the transcript reads back); `instructions_notice` is the `<instructions>` element for an instruction file that changed, a unified diff when shorter than the file. The notice types sit beside their features (`subagent/notice.rs`: `TaskNotice`, `TaskOutcome`, `TaskStall` and `SubagentId`, the one name for a subagent's number; `work/notice.rs`: `WorkNotice`, `WorkState`, with nth-work's `Todo` and `WorkOutcome`). `FrontEnd` (`front_end.rs`) is what a turn reaches the front-end through: the tool handles it passes on to `ToolContext` (`Asker`, `Screen`, `Monitors`, `ContextPreview`, `Wakeup`) and the `Inbox`, which only the turn reads (`Turn.inbox`, from `Held`): no tool sees it through `ToolContext`, and the tools that post to it, `Task` and `Work`, are built with it, so the front-end's one must be the one they hold (`nth`'s runtime makes one per process and hands it to the tools and, on `PreparedRuntime`, to the chat; headless it is `Inbox::default()`, which reaches no model, so they wait). A prompt sent mid-turn (`Inbox::take_prompts`) pre-empts a reply's tool calls: they are answered as interrupted and the turn goes on with your message. An instruction file that changed since the model read it (`ToolContext.watch`, the session's `Watch`) goes in front of the next prompt and between steps, the system prompt kept as it was so its cache holds. Between steps it hands the model what else the `Inbox` holds (`Inbox::take_notices`, then any prompts sent while the tools ran) as a user message. `Session.agent` is the primary agent the session runs as in place of its `mode` (`Session::primary`, `None` when the agent is gone): its prompt replaces the model's persona in the system prompt (memory, skills and agents stay), `ToolContext.agent` limits the tools the turn offers to those it `allows`, its tools write as in act, and `primary/` tells the model when it enters or leaves one mid-conversation (no plan reminders while one runs). `plan/` is plan mode: the plan file's path (`.nth/plans/<id>.md`) and opencode's reminders, appended to the prompt on entering plan mode and on switching to act (`plan::reminder` decides which); in plan mode the `Writable` on `ToolContext` (`plan::writable`) lets write, edit and apply_patch touch the plan file, the memory folder and the current session's Curios source workspace. Your own session's system prompt carries the memory section (`prompts/system/memory.md`: how to save, then the index); the model saves with write and edit, no memory tool, and `memory::ensure_dir` gives the folder a `.gitignore` of `*` before each turn in a repository; when it cannot, the turn fails with `Error::State` naming the folder before the prompt is added or Curios feedback taken (`Session::ready_state`, which readies plan mode's folder the same way), so the memory never lands in git unignored. A subagent never sees or writes it. `usage` is what the session spent: a `Ledger` of one `Spend` per turn (model, steps, the tokens the provider reported — input, output, the cache counts and the reasoning share of the output — the model's `Cost` rates when the front-end's listing gave them, and a `ToolUse` per tool the turn called: calls, failures, time and output), counted by `Turn::run` (`Spend::count`) as each request reports its usage, each `Event::Usage` followed by `Event::Spend`, a copy of the turn's spend so far (a `/compact` opens a spend of its own), and saved with the session; `Spend`, `ToolUse` and `Price` live in nth-protocol for that event and are re-exported here; a spend prices at its stored rates, so `nth usage` works without a listing; a subagent's finished turn goes to `Subagents::take_spent`, and the front-end records it in the parent's ledger. That spend is tagged with the subagent's id, and `subagent/parent.rs` keeps it under one lock with the id up to which subagents were forgotten with a left session: `take_spent` drops a forgotten one's by its tag, and every notice a subagent posts to its parent's model (a task's answer or stall, a work item's return, stall or todo tick) goes through `Parent::tell` under that lock, so none lands in the inbox of the session after the one that was left. Progress goes out as `Event`s over an `mpsc` channel; cancellation is a `CancellationToken` and always leaves `messages` valid to continue from. `subagent/` runs the agents nth-context found: `Subagents` is the registry (one actor task per subagent, owning its `Session`, the jobs waiting and the running one's token, taking `Command`s on a channel, a prompt to queue or a stop, and running the prompts one after another, reporting `SubagentEvent`s to the front-end and publishing a `Status`, its state and queue, on a `watch` that the registry's `state`, `running` and `queued` read; the registry keeps only each child's fixed facts and its handles, and forgetting a child is dropping its command sender), `Task` is the tool the model starts or continues one with (a fresh subagent gets a model-chosen name, retained on continuation and shown in its tab and chat notices; with an `Inbox` it returns at once and the answer lands there as a `<task>` notice; headless it waits), `Spawner` (`spawn.rs`) is how it and `work_assign` start one, on the parent's provider with its share of the tools and an agent's own `model` qualified by it, and `mention::resolve` turns `@name` in a prompt into opencode's instruction to call it. `work/` is the orchestration: a plan of serial cycles of parallel items under `.nth/work/<session>/`, kept on disk by nth-work, written and read through `work_item`, `work_close` and `work_status`. `work_assign` puts a subagent on an item (only in the first cycle with an item not yet closed) with the item as its whole prompt (`assigned.md`) and one extra tool, `work_todo`, bound to the subagent, never to an item, through a `Worker` that never holds `Work` or `Subagents` (a subagent holding its own registry would never end): each call asks `Live`, under `Files`, which item its subagent runs now (`Live::current`). Its `task_id` continues an idle subagent `work_assign` started for this plan in this run (`Live.workers`, which keeps the items each worked on and is what `work_status` lists under `## Subagents`; one the `task` tool started has no `work_todo` and is refused, as is one `Live` still has on a running item), on the same item again or on another, whose prompt is then `reassigned.md`; each job's `Assignment` is the `Worker` with the item it settles and reports stalls for. The subagent's number is taken first (`Subagents::reserve`, which `Subagents::spawn` and `Spawner::spawn` then take as a `Reserved`, whose `Parent` the `Worker` keeps), so the tool is built knowing the id the file keeps, and a number reserved before its session was left never starts. The job's `Done::Work` returns the item file when the turn ends and posts `<work_item>` notices; the actor also reports a stall (`[work]` or `[task] stall_secs` without an event, and again while it stays silent) as a notice that replaces the last one and `SubagentEvent::Stalled`, which wakes the TUI. A turn past its budget is cancelled, and a cancelled turn (budget, stop or a front-end that is gone, which stops it at once) still running `actor::GRACE` later is dropped, its open calls answered as interrupted (`settle_unanswered`) and its job settled as timed out or interrupted; its spend so far stays, since a turn counts into a spend the ledger holds from the start (`Ledger::open`). Events reach the front-end through an outbox, so a front-end that falls behind never stops those clocks. `ToolContext.session` names the session a call runs for, which is how the tools find the plan; it lives under the main checkout (`work::root`, the `Workdir` origin), never under a worktree the session moved into. Todo ticks never wake the model on their own (`Inbox::wakes`): they ride along with a return or a stall, or go between steps. Every change to an item file is made holding `Files`, the lock that also knows which items a subagent of this process runs; an item a gone run of nth left `running` is settled as interrupted on the next work tool call. A subagent's session has `subagent` set and `parent` the session that started it (whose id its requests carry, `Request::parent_session_id`): its system prompt carries the agent's prompt instead of the model's persona and no agents list, and it never gets `task`, `question`, `panel`, `show_user`, `monitor` or `schedule_wakeup`, nor the worktree tools unless its agent's own tool list names them (`task::OPT_IN`, `Agent::names`: the experimenter's), since entering one moves only the child's session. `curios/` is the session's side of Curios and the rules a front-end delivers its feedback and opens curios by. `session.rs` holds the `Session` methods: `curio_store` (`Store::open` from the state root, the store the tools open; none for a subagent), `prepare_curios`, `deliver_curios` (feedback alone starts a turn, never parsed as a prompt), `acknowledge_curios` (after a save) and `Receipts`, through which a turn records each `CurioNotice` (`notice.rs`) in the step that puts it in the history; `curio_root` only caches the main checkout of the state root, never deciding where the store is: kept from the store plan mode readies before a turn, else found (without building the store) once per run when a main-session turn ends, so acknowledgment finds what the tools made; `nth session delete` asks git for the store, on a blocking thread, and reads the cache only when git cannot say (no repository, or no git). Plan mode names and writes the source folder only when the store was readied for the turn (`plan_source_dir`), so a cache kept for deletion never backs one; a store that could not be readied sends the turn end back to git. The rest is all sync; `Poll::run`, `resolve` and `Stores::get` build stores and belong on a blocking thread, while `Delivery` runs on the front-end's loop: `Delivery` (`delivery.rs`) keeps the session's delivery lease and when to retry a refused claim (`CLAIM_RETRY`, telling once that another process delivers) or a failed acknowledgment, a `Poll` reads on a blocking thread and `Delivery::apply` turns what it read into `Polled` (feedback to post, a recorded batch the store still holds to catch up without waking the model); `fresh` is the dedup against the session's receipts, since `CurioDelivery::poll` (the lease, `delivery.rs`) only reads; `resolve` (`open.rs`) decides whose store serves an opened curio (`How`: its own, adopted from an idle session, or a running one's, which keeps it), and `Stores` caches one store per session id for a run.

`context_preview.rs` projects the logical next request without changing the session or inbox: the effective post-compaction messages, the loop's offered tool definitions, pending items and an estimated budget (serialized bytes / 4 plus 2,500 tokens per image, not provider accounting). It excludes the unsent prompt. During a turn, the loop publishes main-session snapshots into `nth-protocol::ContextPreview` once at each committed boundary, a `Phase` (`PendingReply` before a request, `PendingResults` before its calls run, `Ready` after the results and the hand-over, `CompactionRequired`, and `Idle` when the turn or `/compact` ends), never streaming fragments, and builds none unless the slot `builds()`; it never stats instruction files, since the hand-over delivers their changes before the next step's request (only the idle preview shows one still pending).
