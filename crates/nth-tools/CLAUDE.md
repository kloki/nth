# nth-tools

Notes for working in this crate. The root `CLAUDE.md` has the commands, the crate map and the rules every crate keeps.

one module per tool (`read`, `write`, `edit`, `apply_patch`, `bash`, `glob`, `grep`, `webfetch`, `websearch`, `skill`, `question`, `panel`, `show_user`, `monitor`, `schedule_wakeup`, `worktree`); `nth_tools::all()` lists them, each an `Arc<dyn Tool>`, the one way a tool is owned, so a session and its subagents share one list. A path the model names goes through `path::resolve`, which reads a leading `~` as the home directory through `nth_directories::expand_home`, the one `~` rule the config and `/add-dir` share. `read` shows a PNG, JPEG, GIF or WebP to the model instead of reading it as text (`read/image.rs`): its size read from the header first and refused past 50 megapixels (a file past 64 MiB before it is read), then scaled to fit 1920 px and shrunk by quarters to fit `MAX_IMAGE_BYTES`, a re-encoded JPEG or WebP going out as a JPEG, a GIF as a PNG and an animation as its first frame, kept under its hash in `ToolContext.images` (the session's folder, `Store::images_dir` under `Store::images`; the front-ends set it each turn and a subagent shares its parent's) and put on `ToolContext.attachments`, or refused when `ToolContext.takes_images` is off or there is no folder. Any other file is read on a blocking thread only as far as its window needs (each line kept only up to its cut), the rest of its lines counted without being kept so the hint names its length, never past `MAX_TEXT_BYTES` (64 MiB) in (past that the hint says `of more than`); a FIFO, socket or device is refused, and opened non-blocking so one swapped in after the check cannot hang the call. `panel` shows chat, context, diagnostics, plan or work. The main-session `context` tool (`context_preview.rs`) inspects the latest logical request snapshot, the typed `Preview` (the first call of a turn without a front-end watching finds none and asks for one): its overview has budget and entry/tool metadata, and an `entry` index or `tool` name returns one full detail; indices can change with a new snapshot. `show_user` sends a file through the `Screen` on `ToolContext` (`Show::File`, an absolute path) and the TUI opens it in a tab. `schedule_wakeup` sets the `Wakeup` on `ToolContext`, a failsafe while the model waits on background work: when it is due the TUI posts a `<wakeup>` notice to the `Inbox`, which wakes the model; without a front-end it refuses. It returns at once, so the loop ends the turn on a reply whose only calls are wakeups that succeeded, unless something wakeable (a notice other than a work item's todo tick, or a prompt) already waits in the inbox (`Inbox::wakes`), rather than have the model call it again step after step; the doom-loop guard never counts it, since repeating it only replaces the deadline. A main-session turn cancels it once its input is in the history (`prepared_turn`), never between steps, so one the model schedules lasts through the rest of its turn; the TUI cancels it when Esc stops a running turn and when you leave the session or quit. `worktree` is `enter_worktree`, which opens `.nth/worktrees/<name>` through nth-worktree and moves the session there (running the project's `.nth/worktree-setup` in a worktree it just created, `worktree/setup.rs`), and `exit_worktree`, which moves it back; both refuse in plan mode, since the plan file lives under the working directory. `question` reaches you through the `Asker` on `ToolContext`; a front-end without one (`nth run`) has nobody to ask, so the model decides. `bash` passes the model's commands (not yours) through `rtk rewrite` when rtk is on PATH and `[tools.bash] rtk` is on (`bash/rtk.rs`), running what it returns and noting it in the result. bash and the worktree setup script wait for their command through `process::run_to_exit`, which hands the output to a `Receiver` as it arrives (bash streams all of it to the front-end), keeps only a `Tail` of it for the model (the last `max_output_chars` times four bytes, so a chatty command never sits whole in memory) and kills the command's group on any end but its exit, disarming the guard only once bash is reaped. Every waiting tool names its argument `timeout_ms` in milliseconds and rejects `timeout`/`timeout_secs`; `command_output.rs` strips ANSI escapes from command output, and only that, before it reaches the model or the TUI. `grep` and `glob` walk on a blocking thread through `blocking::run`, whose `Stop` a guard in the call's future sets when the session loop drops it (cancel or the ceiling), so the walk, which checks it on every entry, ends with the call and no task watches for it; grep skips a file over 10 MiB and stops after 50,000 files or 10,000 matches, glob after 50,000 matches, each saying so in its result. `webfetch` allows loopback and private/LAN addresses but blocks link-local and cloud metadata hosts at the URL, every redirect and every resolved address, following at most ten redirects itself; it ignores `HTTP(S)_PROXY`, so a proxy cannot bypass that guard. `monitor` leaves a command running in a detached task (`process.rs` is what it shares with bash: `shell` also sets `AGENT=1`, `AI_AGENT=nth` and `AGENT_BROWSER_SESSION` to the session's id, so every command of a session drives one browser and parallel sessions never share one) and reports through `Monitors` on `ToolContext` to the front-end, which puts its stdout lines in the `Inbox` as notices for the model, while stdout and stderr both count toward the flood guard (a line ends at `\n` or `\r\n` and is cut at `MAX_LINE_BYTES`; a lone `\r` redraws it, so a progress bar collapses to its latest state in one line instead of tripping the guard, sent when the line or the watch ends; the inbox cuts a notice line at `NOTICE_LINE_CHARS`); without a front-end it refuses. Its stdin is closed, as every command's, unless the model starts it with `stdin: true`: then `monitor_input` hands text to `Monitors::input`, which queues it for a writer task that owns the pipe (`monitor/stdin.rs`, never an arm of the watch's `select!`, so a command that does not read cannot hold up reading its output; a second handle on the pipe, `Held`, keeps it open until the command is killed, so a stop is never end-of-input after a write cut short, and only the model's `close` releases it early), and waits at most `WRITE_WAIT` for it to be written; what was written comes back to the watch as `Stream::Stdin` lines for the tab and the log, never the inbox or the flood guard. `PostWrite` is what every file-writing tool goes through: `lock` takes the set of path identities (canonical where they exist, sorted, so overlapping patches cannot deadlock and different files run in parallel) and holds them while the tool reads, writes and formats each file through them; once they are dropped the tool asks the language servers about the file and returns the format note and their errors for the model. Every write (write, edit, apply_patch, the BOM put back after a formatter, a kept image) goes through `post_write::write_atomic`: aside in the same folder, then renamed over, so no reader or crash sees half a file; it writes through a symlink to the file it names (the link stays), gives the temporary file an existing file's read, write and execute bits before any byte (setuid and setgid after, since a write clears them), refuses a file the effective user could not write in place, and writes in place only where no rename can work (a folder it may not write in, a file mounted on its own), whose failure says the file may be partly written (`post_write::partly_written`). `apply_patch` keys its plan on the same identities (`post_write::identity`), so two names for one file (`a.txt`, `sub/../a.txt`, a symlink) are one file; a delete or a move's source takes a symlink itself, as `rm` does, never the file it names, locking the link too (resolved again once the locks are held, waiting anew if a path moved meanwhile), and later sections see it gone until one adds it back as a file of its own. It validates every section before writing and, when a write fails, names the completed and unattempted operations and whether the failing file is as it was. Read shares its `Lsp` and touches each file it reads without waiting, so the server is warm by the time the model writes.
