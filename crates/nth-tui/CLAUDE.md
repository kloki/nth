# nth-tui

Notes for working in this crate. The root `CLAUDE.md` has the commands, the crate map and the rules every crate keeps.

The interactive chat (ratatui + crossterm).
The TUI moves the `Session` into a task for each turn and takes it back when the turn ends (`app/turn/`), so Esc cancels cooperatively rather than aborting the task; quitting mid-turn does the same and waits for the turn to save (`app/quit.rs`). What is sent meanwhile is `TurnQueue`'s (`app/turn/queue.rs`): the queue, the turn held for a save, whether a prompt may steer into the running turn, Esc, and whether notices wait for your next prompt or when they wake the model. Its methods return decisions (`Sent`, `AfterTurn`, `Unqueued`) that `App` applies, since the inbox, the prompt and starting a turn are the app's; its rules have table tests of their own.
`App` (`crates/nth-tui/src/app/mod.rs`) runs one `tokio::select!` loop over terminal input, session events, the running turn and background jobs, redrawing on every step. `App::run` takes a `Screen` (`terminal.rs`) and its input stream: the real terminal with crossterm's `EventStream`, which draws each frame inside a synchronized update and hands itself and the stream to your editor on ctrl+g, or in tests `TestScreen`. Between a step and the draw, `App::settle` makes what follows from it hold (the tabs of subagents that answered close), so a draw only draws and records where things went. `App::new` takes one `AppConfig`, which `nth_tui::run` fills, with no builder after it: the `PreparedRuntime` the chat starts on, the process's `Subagents` with the receiver their events come over, the session `Store`, the ChatGPT login, the `Reload`, the prompt history, the model usage, and the clipboard and opener functions (the desktop's in `AppConfig::new`). It installs the runtime through `App::install`, as `/resume` does with the one its `Reload` prepares, so the two cannot drift. A running turn reaches the app through `TurnChannels`, the events, questions and shown tabs, each a channel whose two ends the app keeps. Installing takes the config's `[chat]`, `[layout]` and `[notify]` (`App::apply_config`): a section that changed since the last runtime's replaces the `/settings` toggles, the split width or the notifier, one that did not leaves them, so this run's `/settings` flips outlive a `/resume` whose config says the same; `/resume` then lists the new provider's models at once, so the status bar and the next turn's sizing need no `/models`. Each view's wiring in `app/` is the file named after it (`app/plan.rs` for `plan/`, `app/llm_picker.rs` for `llm_picker/`, `app/question.rs` for `question/`).

The screen is three bands, named as in `docs/ui.md`. Use these names in code and comments:

- **Content panel**: what you look at. `Content` (`app/content.rs`) holds the open tabs, shown in the header, and which one shows; a `Tab` is `Chat` (always first, never closed; until anything is said it shows `hero.rs`, a procedural ASCII field that moves on every tick and ripples under the mouse), `Diagnostics` (`diagnostics/`: `DiagnosticsTab`, which each time the tab opens runs one `Lookup` in the background, the language servers and formatters that apply and the `Programs` on PATH (rtk, agent-browser, `tea` and `gh`), drawn by `view.rs`; `app/diagnostics.rs` wires it and the servers' states on the status bar), `Context` (`/context`, `context.rs`, wired by `app/context.rs`: the main session's scrollable next-request preview, kept with the `ContextPreview` the app hands each turn and the running turn's receiver in `ContextTab`; while visible and idle it is rebuilt from a cloned session at once on your changes (the turn ending, the tab opening or showing, a model, effort, mode, agent or `/add-dir` change, resume or a fresh session), while what arrives per line or per event (a monitor's stdout or end, a subagent's answer or stall, a work item's todo tick, a curio batch, a new listing, the terminal regaining focus) only marks it stale and the one-second tick rebuilds it once, as it does a tab that came into view without input (a resize that splits the panel, a tab closing by itself); while open it follows a running turn's snapshots, subscribed when the turn starts or the tab opens mid-turn (showing what the turn published so far, or waiting for its next step) and dropped when either ends), `File(id)` (`file.rs`: a file the `show_user` tool showed, as markdown or highlighted code, with a watcher task that polls it and sends it again whenever it changes; `app/file.rs` wires them, one tab per path, closed only by you), `Usage` (`usage/`: what the session spent, from `App::spent` in `app/usage.rs`: the session's own ledger, or while a turn's task holds the session the copy taken when it left, with the running turn's last `Event::Spend` on top, so a subagent's turn shows once its spend reaches that ledger; its all-time section also reads every saved session's tool totals, which `UsageTab` keeps with the read that refreshes them, `UsageTab::load_tools`), `Work` (`work.rs`: the work plan as a tree from `nth_work::outline`, which `nth work` draws too; every item names who worked on it, the subagent's name, agent and number and its model with effort, dim once it is done or pending, and the header counts the items per model, `Plan::models`, a model drawn everywhere by `theme::model_spans`, the prompt's label too; a running item's time and calls come from its subagent's tab, found by the subagent's number the item file keeps among the tabs whose description starts with `work `, since one subagent works on several items in turn, and a running item with none is lost; each read puts the item a work subagent runs now in its tab's description; `app/work.rs` reads it after every `work_*` call, a subagent's turn end and the end of each turn), `Plan` (`plan/`: the plan file with the latest turn's changes marked, opened while the file exists, dismissable, and shown again by `/plan` or the next revision; `app/plan.rs` reads it and runs `/approve`; `app/editor.rs` is ctrl+g, which hands the terminal to your editor on a copy of the plan while its tab shows — its diff goes to the model as review feedback, `nth_session::plan::edits` — or of the prompt, whose edits become its text again) or `Keymaps` (`keymaps.rs`: the read-only keyboard reference `/keymaps` opens, scrollable and closed only by you) or `Monitor(id)` (`monitor.rs`, one per running command, closable only once stopped; `app/monitor.rs` wires them and puts each one's stdout lines and end in the inbox as it hears them, never those of a monitor started for a session that was left, `MonitorTabs::forgotten`, and logs them under `Store::monitor_dir`) or `Subagent(id)` (`subagent.rs`: a header, its name, agent, what it was asked, how its turn is doing and last the model `SubagentEvent::Started` said it runs on, and the subagent's own `Chat`; `app/subagent.rs` wires them, and while one shows the prompt talks to it: its label names the agent, Enter queues into its inbox, Esc stops its turn and what waits; the header's queue count is the registry's `queued`, read on every draw), and later ones (Diff) become new variants. From `[layout] split_width` columns, once another tab is open, the panel splits (`Content::panes`): chat on the left, and on the right the last other tab that had the focus (`side`). The focus stays `Content::active`; hovering a pane moves it there. The `panel` tool switches tabs through the `Screen` on `ToolContext`, and `show_user` opens file tabs through it.
- **Input panel**: what you type into. The `Input` enum (`app/input.rs`) picks it: `Input::Prompt` by default, or a widget such as the model picker that swaps in and hands back to the prompt. `/settings` swaps in `settings/`: `ChatSettings` (show thinking, show tool output) starts from the `[chat]` table in the config, lives on `App` for this run only (`/settings` flips it, never writing back; a `/resume` onto a changed `[chat]` starts it over) and every `Chat::draw` lays its transcript out with it. `/connect` swaps in `connect/`: the providers that take an account (ChatGPT today) with a ✓ when connected, then, once Enter starts the browser login (`app/connect.rs`, a `Job` dropped by Esc), its URL to click or copy (`c`) while it waits; a login lists the models again and opens the model picker. `/memory` opens the memory index in a file tab. `/copy` copies the shown chat's latest completed answer as raw Markdown (a subagent's while its tab shows; the latest compaction summary counts as an answer) and `/copy-id` copies the session id. `/rename <title>` saves a session name, shown on the chat tab and terminal; manually named sessions have a star in `/resume`. `nth session rename <id> <title>` names a saved session from the CLI. The model and session pickers filter as you type through `fuzzy.rs` (nucleo), as telescope does. `/` completes nth's commands and then the skills (`command/`); a skill runs by filling its template (`nth_context::skills::parse` and `Skill::invoke`), the same way `nth run "/name args"` does. `@` completes agents, then files (`mention/`), and one starting `../`, `./`, `/` or `~` browses the filesystem a directory at a time (`path.rs`, which `/add-dir` completes with too); a sent `@name` is resolved by the session (`nth_session::subagent::resolve`).
- **Mode**: Tab at the prompt switches plan and act (`app/mode.rs`); `App.selection` (nth-config's `Selection`) holds what every kind of turn runs on and is the one thing the prompt label, the status bar, the model picker, the diagnostics tab and each turn read, so nothing is synced on a switch. Each mode keeps its own model and effort (its `Slots`, from the active `[[profiles]]` entry in the config, or the `model` fallback when there are none). `Slots.subagent` is what subagents run on (a profile's `[profiles.subagent]`; `None` is the parent's model), handed to the session each turn as `TurnEnv::subagent` and to `child_session` (`subagent/child.rs`) through `ChildLlm::subagent` on `ToolContext`; an agent's own `model` still wins. `Slots.clerk` is what the built-in clerk runs on (`[profiles.clerk]`; `None` is the subagents' model), handed over the same way as `TurnEnv::clerk` and `ChildLlm::clerk`; only the built-in has `Agent::clerk` set, so a `clerk.md` replacing it runs as any other subagent. Tab in the model picker cycles its `Target` (plan, act, subagent, clerk), starting on the current mode, and the diagnostics tab shows a row for each of plan, act, subagent and clerk. `/agents` (`agent_picker/`, wired by `app/agent_picker.rs`) runs later turns as a primary agent in place of the mode: `selection.agent`, handed to the session each turn as `Session::agent`, on its own model for this run (`Selection::set_agent`: what it was pinned on — picked by hand, act picked while it runs, or left on — else its `model`, qualified through `Provider::qualify` by `App::set_agent`, at act's effort, else act's), which the model picker reaches as `Target::Agent` while one runs; Tab (`App::toggle_mode`) goes back to the mode, and the prompt's label names the agent in `AGENT_COLOUR`. `app/profiles.rs` cycles the profiles with ctrl+p through `Selection::next_profile` (skipping ones whose provider has no key, or that run on ChatGPT while it is not connected, asked on every cycle so a `/connect` counts) and says the `Cycled` it returns; a model picked by hand for any slot leaves the profile, and the next ctrl+p restores it. The chat takes the `Selection` its runtime prepared, on start and on a `/resume` that prepares another (one that does not keeps the current), put on the session's mode, agent and model (`mode::follow`).
- **Commands**: `!` at the start of the prompt makes it a command (`Prompt::shell`, label `cmd` in yellow). Enter runs it through `Session::shell` on the untimed `Bash` the `PreparedRuntime` hands over, as a turn without the model (`App::start_shell`); the session records it as opencode does, `SHELL_PROMPT` then a bash call and its result, and a replay shows a prompt that `SHELL_PROMPT` joined after a failed turn without it.
- **Mouse** (`app/mouse.rs`): the wheel scrolls the showing tab, a click on the header shows that tab (`header::tab_areas`), a left click in a chat opens the link under it (`Chat::link_at`, from the links `rich::markdown` carries through wrapping) and a right click copies the entry under it (`Entry::clipboard`, through `terminal::copy`, OSC 52), or the status bar's working directory or branch. Each chat records where its last draw put it, so clicks in a subagent's tab work the same. What the pointer is over is a `Target`: the draw records each one with `Areas::target` (a popup over the panes with `Areas::cover`), a chat's links and entries are looked up live, and `App::draw_hover` marks every hit last, so two can show at once: a header tab or chat link turns `theme::HOVER` (magenta), a status bar link `theme::HOVER_STATUS` (white), and a chat entry gets `theme::HOVER_ENTRY` (dark grey) behind it, only where nothing set a background, so hoodrich's code blocks keep theirs. Something new to point at is a `Target` variant, one `Areas::target` call where it is drawn and an arm in `App::click` or `App::right_click`.
- **Status bar**: always `status::ROWS` (2) lines at the bottom. Its git state is `GitBar` (`git/`): the status and the branch's pull request with the two loads that refresh them, each git, `gh` or `tea` call cut off after `git::LOAD_TIMEOUT` so a tool hanging on the network shows nothing until the next change loads again; `app/git.rs` wires it.

Heights are decided bottom-up: the status bar, then the input panel's own `Input::rows()`, then the content panel takes the rest. A view's state lives on `App` (`App.chat`, `App.prompt`), not in the enum variant, so it keeps up with the session and keeps its text while hidden. A tab with state beyond its view keeps it together in one struct (`FileTabs` in `app/file.rs`, `WorkTab`, `PlanTab`, `ContextTab`, or in a feature folder, `<feature>/mod.rs` beside its `view.rs`: `DiagnosticsTab`, `UsageTab`, `CuriosTab`, whose `next()` carries its one-second poll tick too): the view, what it reads and its background job, with a `next()` the loop's `select!` waits on that resolves with the job's result.

Markdown and code go through `rich.rs`, the only module that uses [hoodrich](https://github.com/kloki/hoodrich). Chat messages are concealed markdown. read, write, edit (as a diff) and webfetch output are highlighted by tool (`output_lines` in `chat/render.rs`). The plan tab renders the plan as markdown. hoodrich gives one line per source line, and `rich::wrap` wraps them with their styles kept, because every pane draws pre-wrapped lines. Every tab uses a `Pager` (`pager.rs`) for scrolling, which the keys and wheel move; Home and End scroll the active content to the top and bottom; a monitor's follows the newest line, and the file and plan tabs keep their wrapped lines in a `Cache` until they or the width change. A chat uses the same pager with half-screen pages and draws only a window of its transcript.

Completion notifications (`app/notify.rs`) are suppressed while subagents or monitors run or the inbox has wakeable notices; questions and failures still notify. A plan-mode completion waits for the plan read before deciding which notification to send.

TUI tests render `App` into a `TestBackend` and assert on rows (`rows()` in `app/tests/mod.rs`), so layout changes mean updating row indexes there. A test app is built as the chat's is, `App::new` on `AppConfig::test(session, provider)` (a runtime as an empty config prepares it, with notifications off, the panel never splitting (`split_width` 0), subagents reporting to the app, and a clipboard and opener that go nowhere): `test_app()` is that on an idle provider, `app_on(session, provider)` on yours, `split_at(width)` one that splits from `width` columns, and a test that needs more changes the config (`test_config()`, or `AppConfig::test`) before `App::new`. Turns in tests run against one fake provider, `Scripted` (`app/tests/provider.rs`): a script of replies (events, a failure, a hang, or events once a gate opens), then a fallback for every later request. `app/tests/run.rs` drives the loop itself: `drive` runs `App::run` on a `TestScreen`, which draws into a `TestBackend`, sends each frame's rows over a `watch` and refuses the editor, while the test's script types through a `Driver` and waits for a frame showing some text (`Driver::shows`); dropping the driver ends the input and so the loop. Jobs are injected by starting them on the app before the loop runs. Its apps run in `nowhere()`, a directory under a removed temporary one (never a fixed path such as `/repo`, where a CI may mount the checkout), so the git and forge processes the loop starts fail at spawn and none is in flight while a paused clock jumps; ctrl+g writes its copy to `AppConfig::editor_dir`, which a test points at a temporary directory.
